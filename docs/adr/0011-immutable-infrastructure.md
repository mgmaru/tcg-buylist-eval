# 0011. インフラはイミュータブルにする

- ステータス：採用
- 日付：2026-10-26
- 決定者：kajiwara

## 背景

- GPUサーバーとエージェントの実行環境は、使うときだけ作って終わったら消す（[0005](0005-gpu-environment.md)）。評価環境は、使ったらクリアにして作り直す流れになる。
- 評価では、「なぜ結果が変わったのか」を後から追えることが大事になる（設計書 5.5）。環境が実行ごとに少しずつ違うと、結果の違いがモデルやハーネスによるものか、環境によるものか分からなくなる。
- エージェントは環境を壊す可能性がある（[0003](0003-isolated-execution-environment.md)）。
- インフラの構築の経験を、ほかのハーネスでも使い回せる形で積みたい（[0004](0004-infrastructure-as-code.md)）。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| ミュータブル（動いているサーバーの中を直して使う） | 小さな変更はすぐできる | サーバーごとに状態がずれていく。どの環境で動かしたかを正確に残せない |
| イミュータブル（サーバーの中は変えず、変えるときは作り直す） | 毎回同じ環境から始められる。壊れても作り直せば戻る | 作り直す手順が必要。消えては困るデータは別に扱う必要がある |

## 決定

インフラは、次の原則に従う。

- **動いているサーバーの中は変えない。** SSHで入って設定を変えたり、パッケージを入れたりしない。変えるときは、定義を直してサーバーごと作り直す。
- **消えては困るデータ（状態）は、サーバーと分けて扱う。** サーバーを作り直しても、データは残るようにする。
- **環境を作るものは、バージョンを固定する。** 何で動かしたかを実行記録に残し、同じ環境を作り直せるようにする。

具体的な設計（どのコンポーネントを使うときだけ作り、どれを残すか、残すものをどこに置くか、何をどう固定するか）は、TODOの「インフラの設計」で、コンポーネントを洗い出してから決める。

## 影響

- これまでのADRで決めた置き場所（[0004](0004-infrastructure-as-code.md) の状態ファイル、[0006](0006-cloud-model-authentication.md) のAPIキー、[0010](0010-self-host-langfuse.md) のLangfuseのデータと添付）も、インフラの設計で見直す。違う結論になったら、新しいADRで置き換える。
- 実行記録（`run.yaml`）に、環境を特定する情報を残す（設計書 5.5）。何を残すかはインフラの設計で決める。
