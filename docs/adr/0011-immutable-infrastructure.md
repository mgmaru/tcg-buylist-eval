# 0011. インフラはイミュータブルにする

- ステータス：採用
- 日付：2026-10-26
- 決定者：kajiwara

## 背景

- GPUサーバーとエージェントの実行環境は、使うときだけ作って終わったら消す（[0005](0005-gpu-environment.md)）。評価環境は、使ったらクリアにして作り直す流れになる。
- 評価では、「なぜ結果が変わったのか」を後から追えることが大事になる（設計書 5.5）。環境が実行ごとに少しずつ違うと、結果の違いがモデルやハーネスによるものか、環境によるものか分からなくなる。
- エージェントは環境を壊す可能性がある（[0003](0003-isolated-execution-environment.md)）。
- インフラの構築の経験を、ほかのハーネスでも使い回せる形で積みたい（[0004](0004-infrastructure-as-code.md)）。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| ミュータブル（動いているサーバーの中を直して使う） | 小さな変更はすぐできる | サーバーごとに状態がずれていく。どの環境で動かしたかを正確に残せない |
| イミュータブル（サーバーの中は変えず、変えるときは作り直す） | 毎回同じ環境から始められる。環境の違いが「どのイメージを使ったか」だけになる。壊れても作り直せば戻る | イメージを作る手順が必要。データを持つものは別に扱う必要がある |

## 決定

### 原則

- **動いているサーバーの中は変えない。** SSHで入って設定を変えたり、パッケージを入れたりしない。変えるときは、イメージや定義を直して、サーバーごと作り直す。
- **サーバーの設定は、起動時の自動設定（cloud-initなど）とコンテナだけで行う。** 起動時に取得するものは、すべてバージョンを固定する。
- **データを持つものは、サーバーと分けて残す。**

| 残すもの | 置き場所 |
|---|---|
| Terraformの状態ファイル | S3（[0004](0004-infrastructure-as-code.md)） |
| Langfuseのデータ | データ用のEBS（[0010](0010-self-host-langfuse.md)） |
| 評価の結果 | `results/`（S3にも保存する） |
| モデルの重み | S3 |
| 自作のコンテナイメージ | ECR |

### 固定するもの

| 対象 | 固定の方法 |
|---|---|
| サーバーのイメージ | AWS公式の深層学習用のイメージ（GPUのドライバー入り）など、既製のイメージをAMIのIDで固定する |
| アプリ（実行スクリプト、Ollama、Langfuse） | Dockerのコンテナイメージにし、ダイジェスト（中身のハッシュ）で固定する |
| モデルの重み | S3に置き、ハッシュで固定する。起動時に同じリージョンのS3から取得する |

モデルの重みはサーバーのイメージに焼き込まない。イメージが大きくなり、保管料が増えるため。

### Langfuseの扱い

- Langfuseのアップデートは、サーバーの中で行わない。新しいバージョンのコンテナイメージでサーバーを作り直し、データ用のEBSを付け替える。
- 使わないあいだの停止と起動（[0010](0010-self-host-langfuse.md)）は、サーバーの中身を変えないので、この原則に反しない。

### 進め方

- **M0は、既製のイメージとコンテナで行う。** Packerなどでサーバーのイメージを自作するのは、起動に時間がかかるようになったときや、M1以降に検討する。

## 影響

- 実行記録（`run.yaml`）に、サーバーのイメージのID、コンテナイメージのダイジェスト、モデルの重みのハッシュ、Ollamaのバージョンを残す（設計書 5.5）。
- ECRとS3（モデルの重み、結果）は消さずに残すので、少額の保管料がかかる（モデルの重み約18GBで月数十円の見込み）。
- 設計書 5.5（実行記録）と7章（実行スクリプト）を見直す。
