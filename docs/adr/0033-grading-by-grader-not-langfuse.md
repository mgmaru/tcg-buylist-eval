# 0033. 採点は採点器が行い、LLMは使わない。Langfuseは採点の結果とトレースを受け取る（0007の一部を明確にする）

- ステータス：採用
- 日付：2026-10-30
- 決定者：kajiwara
- 関係するADR：[0007](0007-use-langfuse-for-scoring-and-tracing.md)（Langfuseを使う）、[0010](0010-self-host-langfuse.md)（Langfuseの運用）、[0012](0012-implementation-language-go.md)（実装言語：Go）、[0023](0023-grader-interface.md)（採点器の入出力）

## 背景

- [0007](0007-use-langfuse-for-scoring-and-tracing.md) では、「記録・**採点**・比較・観測にLangfuseを使う」と決めた。背景の表でも、採点の部品に「コードによる採点、LLMによる採点、人間の評価」を挙げ、Langfuseを ◯ にしていた。
- 一方で、そのあとのADRでは、採点は自作の採点器が行うと決めている。
  - [0012](0012-implementation-language-go.md)：採点器はGoの独立したコマンドとして作り、出力JSONと正解データを受け取って点数を出す。
  - [0023](0023-grader-interface.md)：採点器は `grade`（サンプルごとの `metrics.json`）と `summarize`（構成ごとの `summary.json`）の2つのコマンドで、Langfuseへは、その点数を送る。
  - [0010](0010-self-host-langfuse.md)：正式な記録はCSVとし、Langfuseは比較と分析に使う。
- そのため、「採点するのは採点器か、Langfuseか」「採点にLLMを使うのか」が、読み手によって違って読めてしまう。
- Langfuseには、LLMに出力を採点させる機能（LLM-as-a-judge）もある。使うかどうかは、どのADRにも書いていなかった。
- このタスクの答えは、カードのパック・番号・仕様・価格など、正解データとの比較で正誤が決まるものである。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. LangfuseのLLMによる採点（LLM-as-a-judge）で採点する | 採点のコードを書かずに済む。自由な文章の答えも採点できる | 採点が揺れる。採点のたびにAPIの費用がかかる。Claudeは被験モデルでもあるので、Claudeに採点させると偏りが入るおそれがある |
| B. 採点器とLLMの両方で採点する | 採点器が見落とす誤りを、LLMが拾えるかもしれない | 2つの点数のどちらを正とするかが決まらない。A の弱い点も残る |
| **C. 採点は採点器だけが行い、LLMは使わない。Langfuseは、採点器が出した点数とトレースを受け取る** | 同じ出力からは、いつも同じ点数が出る。費用がかからない。偏りが入らない | 自由な文章の答えは採点できない（このタスクには、そういう答えはない） |

## 決定

**C にする。**

- **採点は、採点器（Go）だけが行う。** 出力と正解データを、決まった手順で突き合わせる（[0023](0023-grader-interface.md)）。
- **採点にLLMは使わない。** LangfuseのLLMによる採点（LLM-as-a-judge）の機能も、このタスクでは使わない。
- **Langfuseは、受け取って保存・表示する場所とする。** Langfuseが受け取るのは、次の2つ。
  - 実行スクリプトが送るトレース（プロンプト、出力、トークン数、時間）
  - 採点器が出した点数（実行スクリプトが、`metrics.json` の中身をスコアとして送る）
- **Langfuseの中で、点数を作ったり直したりしない。** 正式な点数は、採点器が出した `metrics.json`・`summary.json` とCSVである（[0010](0010-self-host-langfuse.md)）。
- [0007](0007-use-langfuse-for-scoring-and-tracing.md) の「採点にLangfuseを使う」は、「**採点の結果を記録し、比べるのに**Langfuseを使う」と読む。

このシステムで、LLMを使うのは次の2か所だけになる。

| 役割 | LLM |
|---|---|
| タスクを解く（被験エージェント） | 使う。評価される側 |
| 正解データの下書き（`gold-draft/prompt.md`） | 使う。人が全行を確かめる前の下書きだけ |
| 採点 | 使わない |
| 記録・比較・観測（Langfuse） | 使わない |

## 理由

- **このタスクには、正解データとの比較で決まる正解があるため。** パック・番号・仕様・価格は、合っているかどうかを手順で判定できる。LLMに判断させる余地がない。
- **同じ出力から、いつも同じ点数を出すため。** 被験ハーネスの改善の効果を測るには、物差しが揺れてはいけない。LLMによる採点は、同じ出力でも点数が揺れる。A・B を選ばなかったのはこのため。
- **採点に偏りを入れないため。** Claudeは被験モデルでもある。Claudeに採点させると、Claudeの出力に有利な偏りが入るおそれがある。
- **費用をかけないため。** 採点器による採点は、何度繰り返してもAPIの費用がかからない。
- **Langfuseがなくても、採点と成績表を出せるようにするため。** 採点をLangfuseに頼ると、Langfuseを立てるまで評価が進まない。採点器が採点し、Langfuseは結果を見る道具にしておけば、Langfuseを立てる前でも評価できる（[0010](0010-self-host-langfuse.md) で、Langfuseは採点器とCSVの出力ができてから構築すると決めている）。

## 影響

- Langfuseを立てるとき（TODO 6章）に、LLMによる採点の機能は設定しない。そのためのAPIキーも、Langfuseに登録しない。
- 実行スクリプトがLangfuseに送るスコアは、`metrics.json` の値をそのまま写したものにする。Langfuseの側で、点数を計算し直さない。
- 設計書の Langfuse の説明（3.1、9.1）を、この形に合わせて直す（TODO 3章でまとめて直す）。
- 見直すきっかけ：自由な文章の答えを評価するタスク（要約など）を作るとき。そのタスクでは、LLMによる採点を検討する。
