# 0035. サンプルのメタ情報（meta.yaml）の項目と、そのスキーマ

- ステータス：採用
- 日付：2026-10-30
- 決定者：kajiwara
- 関係するADR：[0016](0016-task-folder-per-task.md)（タスクごとのフォルダ）、[0023](0023-grader-interface.md)（採点器の入出力）、[0028](0028-unnumbered-cards-out-of-m0.md)（対象外のカード）、[0031](0031-schema-kind-and-file-format.md)（スキーマの種類とファイルの書き方）、[0034](0034-sample-id-naming.md)（サンプルID）

## 背景

- サンプルごとに、`samples/<サンプルID>/meta.yaml` を置く（[0016](0016-task-folder-per-task.md)）。採点器の `grade` も、このファイルを受け取る（[0023](0023-grader-interface.md)）。
- 設計書 5.1 には、出典・店舗・更新日・収集日・段と列・枚数・世代・dev／test・`gold_version` の案があった。
- そのあとの決定で、`meta.yaml` に記録することが増えた。
  - 下書きに使ったモデル（`gold-guideline.yaml` の G-02）
  - 外したカードと、その理由（G-04、G-07、[0028](0028-unnumbered-cards-out-of-m0.md)）
  - 確定したあとで直した記録（G-08）
- 1枚目の買取表には、更新日が書かれていなかった。出典のURLには、追跡用の部分（`?a=…&s=20`）が付いていた。
- 人が書き、採点器と人が読むファイルなので、形を決め、機械で確かめられるようにしておきたい。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 設計書 5.1 の項目のまま。スキーマは作らない | 手間がない | 下書きのモデルや外したカードを書く場所がない。書き間違いに気づけない |
| **B. 設計書 5.1 の項目に、下書き・外したカード・直した記録を足す。スキーマ（JSON Schema）を YAML で書く** | 決まったことを、すべて1か所に書ける。書き間違いを機械で見つけられる | スキーマを作り、直していく手間がかかる |

## 決定

**B にする。**

- `meta.yaml` の項目は、次のとおり。

| 項目 | 必須 | 内容 |
|---|---|---|
| `sample_id` | ◯ | サンプルID。フォルダ名と同じ（[0034](0034-sample-id-naming.md)） |
| `source.url` | ◯ | 出典のURL。**追跡用の部分（`?` から後ろ）は外す** |
| `source.shop` | ◯ | 店舗の名前 |
| `source.updated_at` | ◯ | 買取表に書かれた更新日。**書かれていなければ、投稿日** |
| `source.updated_at_from` | ◯ | `updated_at` をどこから取ったか：`buylist`（買取表）／`post`（投稿日） |
| `source.collected_at` | ◯ | 画像を保存した日 |
| `layout.rows`、`layout.cols` | ◯ | 段の数、列の数 |
| `card_count` | ◯ | 買取表に載っているカードの枚数（外したカードも含む） |
| `era` | ◯ | 載っているカードの世代（分析用） |
| `split` | | dev／test。M0では使わない |
| `gold_version` | ◯ | 正解データの版。1から始める |
| `draft.model`、`draft.via`、`draft.at` | ◯ | 下書きに使ったモデル、使った手段（APIなど）、日付 |
| `excluded` | ◯ | 外したカードの一覧：`row`、`col`、`name`、`reason`（`no_pack_number`：パックごとの番号がない／`unresolved`：特定を確定できない）、`note`。なければ空の一覧 |
| `history` | ◯ | 確定したあとで直した記録の一覧：`version`、`date`、`change`。なければ空の一覧 |

- スキーマは `tasks/<タスク名>/schemas/meta.schema.yaml` に置く。**データが入れ子のあるYAMLなので JSON Schema で書き、人が読みながら `meta.yaml` を書くので、ファイルは YAML にする**（[0031](0031-schema-kind-and-file-format.md)）。

## 理由

- **決まったことを書く場所を、1か所にまとめるため。** 下書きのモデル、外したカード、直した記録は、どれもサンプルごとに変わり、あとで成績を読むときに要る。サンプルごとのファイルは `samples/<サンプルID>/` にまとめると決めているので、`meta.yaml` に足す。A を選ばなかったのはこのため。
- **外したカードの理由を、決まった値にするのは、** あとで「番号がなくて外した」「特定できずに外した」を数え分けられるようにするため。前者はタスクの範囲の問題、後者は正解データを作る側の問題で、意味が違う。
- **`updated_at` をどこから取ったかを残すのは、** 更新日と投稿日では意味が少し違うため。買取表によっては、投稿日より前の日付の表を投稿することもある。
- **出典のURLから追跡用の部分を外すのは、** 投稿を指すのに要らず、誰がどこから共有したかの情報が混じるため。
- **スキーマを作るのは、** 書き間違い（必須の項目の抜け、日付の形の誤り）を、採点の前に機械で見つけるため。正解データの列の定義（[0019](0019-gold-schema-machine-readable.md)）と同じ考え方。

## 影響

- 1枚目のサンプル（`magi-nagoya-20261030`）の `meta.yaml` を、この形で書く。
- `gold-guideline.yaml` の S-02 で、この形に沿って `meta.yaml` を書く。
- 採点器の `grade` は、`meta.yaml` をこのスキーマで確かめてから使う。`layout` は、出力の段・列の数を確かめるのに使う。
- `task.yaml` に、このスキーマの場所を書く。
- 見直すきっかけ：サンプルごとに記録したいことが、新しく出てきたとき。
