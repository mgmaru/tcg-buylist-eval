# 0008. 環境の準備と実行：M0は自作の実行スクリプト

- ステータス：採用
- 日付：2026-10-26
- 決定者：kajiwara
- 調査：[評価フレームワークの比較](../research/execution-frameworks.md)

## 背景

Langfuseは、**環境の準備・リセット** と **エージェントの自動実行** を持っていない（[0007](0007-use-langfuse-for-scoring-and-tracing.md)）。これらを、自作の実行スクリプトで行うか、既製の評価フレームワークを使うかを決める必要がある。

これまでの決定で、前提が次のように変わっている。

- **APIキーを使う**（[0006](0006-cloud-model-authentication.md)）。評価フレームワークの多くはAPIキーが前提なので、それが問題にならない。
- **ローカルのモデルも使う**（[0002](0002-compare-cloud-and-local-models.md)）。クラウドのモデルとローカルのモデルを同じ仕組みで呼べれば、「ランタイムの差」が結果に混ざりにくい。
- **隔離が必須**（[0003](0003-isolated-execution-environment.md)）。

## 検討した選択肢

| 選択肢 | 特徴 | 良い点 | 弱い点 |
|---|---|---|---|
| 自作の実行スクリプト | 設計書 7章の手順を自分で書く | 中身をすべて把握できる。評価の仕組みを作る練習になる。M0のH0（ツールなし）なら小さく作れる | 並列実行、ログの管理、繰り返し実行を自分で作る必要がある |
| Inspect AI | 英国AI Security Instituteなどが開発（MITライセンス）。DockerやKubernetesのサンドボックスで動かせる。Claude Code、Codex CLI、Gemini CLIも動かせる | モデルの直接の呼び出しとエージェントのCLIを同じ仕組みで扱える。複数の指標を返す採点、繰り返し実行、並列実行、時間やトークンの上限、ログの画面がそろっている | 覚えることが多い。ローカルのモデルに画像を渡せるかは要確認 |
| Harbor | Terminal-Benchの開発者による評価フレームワーク（Apache-2.0）。コンテナで並列実行できる | 対応するエージェントのCLIとサンドボックスが多い | 画像を入力として渡す方法がない。H0のようなモデルの直接の呼び出しに向かない |
| coder_eval | タスクをYAML 1ファイルで書く | タスクの定義が簡単 | 2026年7月に公開されたばかり。エージェント専用。匿名の利用データを既定で送る |

どれもLangfuseとの連携は組み込まれていない。

## 決定

- **M0は自作の実行スクリプト** で行う。
  - H0はモデルのAPIを1回呼ぶだけなので、AnthropicのSDKと、OpenAI互換のクライアント（ローカルのモデル用）があれば足りる。規模は採点器を除いて300〜500行程度の見込み。
  - 両方のモデルを同じ実行スクリプトから呼び、ランタイムを揃える。
  - 実行スクリプトは、エージェントの実行環境（[0005](0005-gpu-environment.md)）のDockerコンテナの中で動かす。
- **採点器は、フレームワークに依存しない関数** として作る（出力JSONと正解CSVを受け取り、指標を返す）。あとでフレームワークに移るときも、そのまま使えるようにする。
- **M2の前に、Inspect AIへの移行を見直す。** M0の採点器ができたら、半日〜1日の試し（ローカルのモデルに画像を渡せるか、コンテナの中から動かせるか、Langfuseに送れるか）を行う。

## 影響

- 実装言語はPythonを前提とする（AnthropicのSDK、LangfuseのSDK、Inspect AIがそろうため）。正式な決定はTODO 1.1で行う。
- Inspect AIに移る場合、実行スクリプト（設計書 7章）はInspectの仕組みの上に作り直す。採点器は関数のまま組み込む。
