# 0008. 環境の準備と実行：自作か評価フレームワークか

- ステータス：提案
- 日付：2026-10-26
- 決定者：kajiwara

## 背景

Langfuseは、**環境の準備・リセット** と **エージェントの自動実行** を持っていない（[0007](0007-use-langfuse-for-scoring-and-tracing.md)）。これらを、自作の実行スクリプトで行うか、既製の評価フレームワークを使うかを決める必要がある。

これまでの決定で、前提が次のように変わっている。

- **APIキーを使う方向になっている**（[0006](0006-cloud-model-authentication.md)）。評価フレームワークの多くはAPIキーが前提なので、それが問題にならない。
- **ローカルのモデルも使う**（[0002](0002-compare-cloud-and-local-models.md)）。クラウドのモデルとローカルのモデルを同じ仕組みで呼べれば、「ランタイムの差」が結果に混ざりにくい。
- **隔離が必須**（[0003](0003-isolated-execution-environment.md)）。

## 検討した選択肢

| 選択肢 | 特徴 | 良い点 | 弱い点 |
|---|---|---|---|
| 自作の実行スクリプト | 設計書 7章の手順を自分で書く | 中身をすべて把握できる。評価の仕組みを作る練習になる。M0のH0（ツールなし）なら小さく作れる | 隔離、並列実行、ログの管理を自分で作る必要がある |
| Inspect AI | 英国AI Security Instituteなどが開発。DockerやKubernetesのサンドボックスで動かせる。Claude CodeやCodex CLIなど外部のエージェントも実行できる | 隔離の仕組みが標準である。採点の仕組みやログもそろっている | 覚えることが多い。Inspectの作法に合わせる必要がある |
| Harbor | Terminal-Benchの開発者による評価フレームワーク。コンテナで並列実行できる | 独自のベンチマークや環境を作れる | コーディングエージェント向けの作りで、画像を読むタスクに合うか要確認 |
| coder_eval | タスク（プロンプト、エージェントの設定、サンドボックス、成功条件）をYAML 1ファイルで書く | タスクの定義が簡単 | コーディングエージェント向けの作りで、画像を読むタスクに合うか要確認 |

## 決定（提案）

まだ決めない。調べたうえで、自作とInspect AIを中心に比べる。

採用にするために調べること：

- ローカルのモデル（Ollama、vLLMなど）を呼べるか
- 画像を入力として渡せるか
- Dockerのサンドボックスで動かせるか。AWS上でも動かせるか（[0005](0005-gpu-environment.md)）
- 自作の採点器を組み込めるか（設計書 8章）
- Langfuseにトレースとスコアを送れるか（[0007](0007-use-langfuse-for-scoring-and-tracing.md)）

## 影響

- 評価フレームワークを使う場合、実行スクリプト（設計書 7章）と採点器（設計書 8章）は、そのフレームワークの仕組みの上に作る。ディレクトリ構成（設計書 4章）も見直す。
- 自作にする場合も、M2以降でタスク数や繰り返し回数が増えたら、評価フレームワークへの移行を見直す。
