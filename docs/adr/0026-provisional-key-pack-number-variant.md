# 0026. 仮のキーは「パック＋番号＋仕様」で作る（公式サイトのIDは使わない）

- ステータス：提案
- 日付：2026-10-29
- 決定者：kajiwara（未決定。PRでレビューする）
- 関係するADR：[0019](0019-gold-schema-machine-readable.md)（正解データの列の定義）、[0027](0027-provisional-key-variant.md)（仕様の扱い）、[0028](0028-unnumbered-cards-out-of-m0.md)（番号のないカード）、[0029](0029-provisional-key-pack-name.md)（パックの名前）
- 調査：[docs/research/card-data-sources.md](../research/card-data-sources.md)

## 背景

- カード名だけでは、カードを一意に決められない（設計書 2.2）。主キーはカードDBの `card_id` にする予定だが、カードDBを作るのはM1から。M0では **仮のキー** を使う。
- 設計書には、仮のキーの案が2つある。案1「パック名＋カード番号」と、案2「公式サイトのカードID」。
- M0の最初の題材は、BW期の買取表（トレキング NEW AKIHABARA、21枚）。高い値が付くのは、SR・URなどのシークレットレア（番号が収録数を超えるカード）が中心。
- 公式のカード検索を全件調べたところ、次のことがわかった（調査の1章）。
  - DP（2006年）より前のカードは載っていない。
  - **BW期のシークレットレアは載っていない**（ブラックコレクションは001〜053/053だけで、レシラムSR 055/053がない）。
  - 1ED・アンリミ・ミラーなどの仕様を区別しない。
- 一方、パック＋番号なら、ショップや有志のWikiでも照合できる。シークレットレアも載っている（調査の2章）。
- ただし、パック＋番号だけでは一意にならない場合がある（調査の4章）。
  - BW1のブラックコレクションとホワイトコレクションは、型番がどちらも「BW1」で、番号の体系も同じ。
  - 同じパック・同じ番号でも、1EDとアンリミ、ミラーなどで価格が違う。プロモでは、同じ番号でスタンプだけが違うカードもある（013/XY-P のデデンネ）。
  - そもそもパックごとの番号がないカードもある（旧裏・neo、DP1〜DP5、番号のないプロモ）。これは [0028](0028-unnumbered-cards-out-of-m0.md) で扱う。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 公式サイトのカードID（案2） | 公式が発行した一意のIDで、表記ゆれがない | **BW期のシークレットレアと、DPより前のカードにIDがない。** 最初の題材の高額カードを表せない。仕様も区別しない |
| B. パック＋番号（案1） | 公式以外のサイトでも照合できる。シークレットレアも表せる | 1EDとアンリミ、ミラーなどを区別できない。間違った仕様の価格が紐付く |
| **C. パック＋番号＋仕様** | B の良い点に加えて、仕様の違いも表せる。ショップが価格を付ける単位と揃う | 仕様の値の決め方と、買取表で区別されていないときの扱いを決める必要がある（[0027](0027-provisional-key-variant.md)） |
| D. 型番＋番号 | カードに印刷されている情報だけで作れる | ブラックコレクションとホワイトコレクションの「BW1 055/053」のように、一意にならない |

## 決定

**C にする。** 仮のキーは、**パック・番号・仕様** の3つを `#` でつないだ文字列にする。

```
<パック>#<番号>#<仕様>

ブラックコレクション#055/053#指定なし
プラズマゲイル#077/070#1ED
BWプロモ#001/BW-P#標準
```

| 要素 | 内容 |
|---|---|
| パック | カードが入っていた商品（拡張パック、デッキ、プロモなど）。**型番ではなく商品の単位** にする。名前のそろえ方は [0029](0029-provisional-key-pack-name.md) |
| 番号 | カードに印刷されている番号を、分母やプロモの記号も含めて、そのまま書く（例：`055/053`、`001/BW-P`） |
| 仕様 | 1ED・アンリミ・ミラーなど。決まった値の中から選ぶ（[0027](0027-provisional-key-variant.md)） |

- 型番（BW1など）は、仮のキーには入れず、正解データの `set_code` の列に別に持つ。
- 正解データの `pack`・`number` の列と、仮のキーの中身を揃える。仮のキーは、この3つの列から機械で作れるようにする。

## 理由

- **A を選ばなかったのは、最初の題材の高額カードを表せないため。** BW期の買取表は、シークレットレアが中心。公式のIDがないカードが必ず出るので、案2ではM0の正解データを作りきれない。DPより前のカードを扱う買取表でも同じことが起きる。
- **パック＋番号なら、複数のサイトで確かめられるため。** ショップ（遊々亭、カードラッシュ、ネットオフ）とWiki（ポケモンカードWiki）は、どれもパックと番号でカードを並べている。1つのサイトに抜けがあっても、ほかのサイトと突き合わせられる。正解データは成績を測る物差しなので、確かめる手段が多い方がよい。
- **B ではなく C にしたのは、間違った仕様の価格を紐付けないため。** このタスクで一番重く見るのは、誤答（間違ったカードに価格が紐付くこと）。1EDとアンリミでは価格が違うので、仕様を取り違えると、Card Pulseのデータが気付かれないまま汚れる。
- **パックを型番ではなく商品の単位にしたのは、** 型番では一意にならない例（BW1の055/053）が、最初の題材でもう見つかっているため。公式サイトも、ブラックコレクションとホワイトコレクションを別のパックとして扱っている。
- **D を選ばなかったのも、同じ理由。**
- **番号を印刷の通りに持つのは、** プロモの番号（`001/BW-P`）のように、番号そのものに区別の情報が入っているため。分母を落とすと、収録数の違うパックの間で取り違える。

## 影響

- 設計書 2.2 の仮のキーの説明と、5.2 の `provisional_key` の例（`プラズマゲイル#077/070`）を、この形に直す。
- `gold.schema.yaml` の `provisional_key` の説明と形を、この形にする（[0019](0019-gold-schema-machine-readable.md)）。
- 出力のスキーマ（`output.schema.json`）の `identification` に、仕様の欄を足す。採点器は、出力の `pack`・`number`・仕様から仮のキーを作って比べる。
- 正解データの作成ルール（`docs/gold-guideline.md`）に、パック・番号・仕様を、公式と公式以外の複数のサイトで突き合わせて確かめることを書く。
- 公式サイトのIDは使わないが、DP以降の通常のカードの印刷内容（HP、ワザ）を確かめるのには使える。M1でカードDBを作るときに、参照用の列として持つかを決める。
- 見直すきっかけ：M1でカードDBを作り、`card_id` に置き換えるとき。
