# 0025. 差し込み口のうち、M0 で作る範囲

- ステータス：採用
- 日付：2026-10-28
- 決定者：kajiwara
- 関係するADR：[0016](0016-task-folder-per-task.md)〜[0024](0024-show-harness-changes-and-effects.md)（差し込み口の設計）

## 背景

- 差し込み口の設計（[0016](0016-task-folder-per-task.md)〜[0024](0024-show-harness-changes-and-effects.md)）は、タスクや被験エージェントを差し替えるための境界の形を決めるものである。
- 一方で、M0 では第一の目的を優先し、汎用の仕組みを作り込みすぎないことにしている（設計書 0.3）。タスクが1つしかない段階で、汎用の仕組みを作り込むと、M0 の完了が遅れる。

## 検討した選択肢

| 選択肢 | 内容 | 良い点 | 弱い点 |
|---|---|---|---|
| A. 差し込み口を作らない | M0 は買取表のタスクだけを、決め打ちで作る | 一番早い | あとでタスクを足すときに、作り直しが大きくなる |
| **B. 境界の形だけを作る** | 決めた境界の形（ファイルの形、受け渡しの決まり）は M0 から守る。汎用の仕組み（タスクを自動で見つけて読み込む仕組みなど）は作らない | あとでタスクを足すときの作り直しが小さい。M0 の手間の増え方も小さい | 境界の形が正しいかは、2つ目のタスクを扱うまで分からない |
| C. 汎用の仕組みまで作る | タスクや被験ハーネスを自動で見つけて読み込む仕組みまで作る | タスクを足すのが一番楽 | タスクが1つしかない段階では、何が汎用に必要か分からず、作り込みが無駄になりやすい。M0 が遅れる |

## 決定

**B にする。**

| 項目 | M0 で作る | 形だけ決めて、作らない |
|---|---|---|
| タスク | 1つ。`task.yaml` を置く | 2つ目のタスク |
| サンプル | 1〜3件 | dev/test の分割（M2） |
| モデル | `opus-5-5`、`qwen3-8-27b` の2つ | ほかのモデル |
| 被験ハーネス | `direct-api` の H0 だけ | H1〜H3、`external-cli` |
| 被験構成 | `opus-h0`、`qwen-h0` の2つ | ― |
| 採点器 | `grade` と `summarize` | ほかのタスクの採点器 |
| 決まりの確認 | `task.yaml`・被験構成・`metrics.json` の形を、スキーマで確かめる | 汎用のプラグインの仕組み |
| 改善の記録（[0024](0024-show-harness-changes-and-effects.md)） | 形だけ（H0 しかないため） | 元にした構成との差の表示（M1 で部品を足すときから） |

2つ目のタスクを扱うときに、この境界で本当に足りるかを確かめ、必要なら直す。

## 理由

- **あとの作り直しを小さくしつつ、M0 を遅らせないため。** 境界の形（ファイルの形、受け渡しの決まり）を守るだけなら、M0 の手間はあまり増えない。一方で、守っておけば、2つ目のタスクを足すときに、実行スクリプトやレポートを書き直さずに済む。
- A を選ばなかったのは、決め打ちで作ると、買取表のタスクに特有の処理が実行スクリプトやレポートに混ざり、あとで取り除くのが大変になるため。
- C を選ばなかったのは、タスクが1つしかない段階では、何が汎用に必要かが分からないため。必要になる前に作った汎用の仕組みは、外れることが多い。
