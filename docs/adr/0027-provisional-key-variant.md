# 0027. 仮のキーの仕様は「版・加工・スタンプ」の軸に分け、確かめられない軸は「指定なし」にする

- ステータス：提案
- 日付：2026-10-29
- 決定者：kajiwara（未決定。PRでレビューする）
- 関係するADR：[0026](0026-provisional-key-pack-number-variant.md)（仮のキーは「パック＋番号＋仕様」）
- 調査：[docs/research/card-data-sources.md](../research/card-data-sources.md)

## 背景

- 仮のキーには、1ED・アンリミ・ミラーなどの **仕様** を含める（[0026](0026-provisional-key-pack-number-variant.md)）。同じパック・同じ番号でも、仕様が違えば価格が違うため。
- **仕様は1つとは限らない。** たとえば「ミラーで、かつ1ED」のように、性質の違う仕様が重なるカードがある。プロモには、同じ番号でスタンプだけが違うカードもある（013/XY-P のデデンネ。調査の3.3）。
- **ミラーには種類がある**（マスターボールミラー、モンスターボールミラーなど）。種類によって価格が違い、**どんな種類があるかは世代や商品によって違う。**
- 仕様の区別のしかたは、サイトや店によって違う（調査の2章）。
  - 遊々亭は、BW期の1EDとアンリミを区別しない。
  - カードラッシュは、商品名に「(1ED)」「(アンリミ)」を書いて区別する。書いていなければ「1EDではないもの、または選べないもの」。
- 買取表も、店によって仕様を書いたり書かなかったりすると考えられる。書かれていなければ、正解データでも仕様を決められない。
- 画像から仕様を読み取れるとも限らない。1EDのマークは小さく、買取表の画像では見えないことが多い。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 仕様を自由な文字で書く | 何でも書ける | 「1ED」「1st」「初版」のように表記がゆれ、機械で比べられない |
| B. 仕様を1つの値で持つ（`1ED`、`ミラー` などから1つ選ぶ） | 単純 | 「ミラーで、かつ1ED」を表せない。組み合わせごとに値を作ると、値が増え続ける |
| C. 仕様を複数選べる値の集まりで持つ（`1ED+ミラー`） | 重なりを表せる | 同じ種類の仕様が2つ選ばれる（`1ED+アンリミ`）のを防げない。どの性質が「わからない」のかを表しにくい |
| **D. 仕様を軸に分け、軸ごとに1つの値を持つ。確かめられない軸は「指定なし」にする** | 重なりを表せる。軸ごとに「わからない」を表せる。ありえない組み合わせ（1EDかつアンリミ）が起きない | 軸を決める必要がある。新しい種類の仕様が出てきたら、軸を足す必要がある |

## 決定

**D にする。** 仕様を次の3つの軸に分け、軸ごとに決まった値から1つ選ぶ。

| 軸 | 値 | 例 |
|---|---|---|
| 版 | `1ED`、`アンリミ`、`なし`、`指定なし` | 1EDのない世代（サン＆ムーン以降など）は `なし` |
| 加工 | `ノーマル`、ミラーの種類の名前、`指定なし` | `マスターボールミラー`、`モンスターボールミラー` |
| スタンプ | `なし`、配布元などの名前、`指定なし` | `コロコロ`、`ポケモンパン` |

- **どの軸も、確かめられなければ `指定なし` にする。** 買取表に書かれておらず、画像からも決められないとき。
- **`なし` と `指定なし` は分ける。** `なし` は「確かめた結果、その軸の仕様がない」、`指定なし` は「確かめられない」。
- **ミラーは、種類の名前まで分ける。** `ミラー` だけの値は作らない。
- 加工とスタンプの値の一覧は、最初から全部は作らない。題材に出てきたものから足す。足すときは、`gold.schema.yaml` と `output.schema.json` の両方を同時に直す。
- 仮のキーでは、軸を「版・加工・スタンプ」の順に並べる（[0026](0026-provisional-key-pack-number-variant.md)）。
- **採点は軸ごとに比べる。** 正解がその軸で `指定なし` なら、その軸は比べない。`指定なし` でない軸がすべて合い、パックと番号も合えば正解とする。

## 理由

- **A を選ばなかったのは、機械で比べられないため。** 採点器は仮のキーを文字列として比べる。表記がゆれると、合っているのに誤答になる。
- **B を選ばなかったのは、仕様の重なりを表せないため。** 「ミラーで、かつ1ED」のようなカードを、1つの値では表せない。組み合わせごとに値を作ると、値が増え続ける。
- **C ではなく D にしたのは、** 1EDとアンリミのように同じ種類の仕様は、同時に選ばれることがないため。軸に分けておけば、ありえない組み合わせが入らない。また、「版はわからないが、加工はわかる」のように、軸ごとに確かめられたかどうかを表せる。
- **確かめられない軸を `指定なし` にするのは、物差しに推測を入れないため。** 正解データは成績を測る物差しで、人が確かめた事実だけを書く（設計書 10.2）。買取表に書かれていない仕様を推測で決めると、モデルが正しく「わからない」と答えても誤答になる。
- **`指定なし` の軸を比べないのは、** 買取表に書かれていない情報で、モデルの成績を測れないため。その一方で、書かれている軸は比べる。仕様の取り違えは、間違った価格の紐付けにつながるため。
- **`なし` と `指定なし` を分けたのは、** M1でカードDBに移すとき、`なし` は1つのカードに対応するが、`指定なし` は複数のカードの候補が残るため。
- **ミラーを種類まで分けるのは、** 種類によって価格が違い、Card Pulseでは区別が欠かせないため。仮のキーの段階から分けておけば、カードDBに移すときに情報を失わない。

## 決めるために必要なこと

- **正解の軸が決まっていて、出力が `指定なし` のときの扱い。** 案：その軸を読み取れなかったとして「不明」と同じに扱う（誤答にはしない）。誤答率を最も重く見る方針に合う。
- **正解の軸が `指定なし` で、出力が `1ED` などを答えたときの扱い。** 案：比べない（正解として扱う）。ただし、知識で補った可能性があるので、失敗の分類（設計書 9.2）の「知識による補完」の候補として記録する。
- **3つの軸で足りるか。** 世代ごとの加工の種類を調べたうえで（下の影響）、軸を足す必要がないかを確かめる。

## 影響

- `gold.schema.yaml` と `output.schema.json` に、版・加工・スタンプの3つの欄と、それぞれの選べる値の一覧を足す。
- 採点器の同定の判定（設計書 8.2）に、軸ごとの比べ方を足す。
- タスク仕様（`docs/task-spec.md`）に、確かめられない軸は `指定なし` と答えることを書く。
- 正解データの作成ルール（`docs/gold-guideline.md`）に、買取表や画像で確かめられた軸だけを書き、推測では埋めないことを書く。
- **Card Pulseでは、世代ごとの加工の種類（ミラーの種類など）まで区別する。** どの世代・どの商品に、どの種類があるかを調べ、M1のカードDBの材料にする。
- 見直すきっかけ：買取表を増やして、新しい種類の仕様が出てきたとき。M1でカードDBに移すとき。
