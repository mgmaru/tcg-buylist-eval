# 0060. 結果は、タスク・被験構成・測定・サンプル・繰り返しの順の階層に置き、run_id はその道すじにする（0023の一部を置き換え）

- ステータス：採用
- 日付：2026-11-04
- 決定者：kajiwara
- 関係するADR：[0016](0016-task-folder-per-task.md)（タスクごとのフォルダ）、[0018](0018-results-include-subject-info.md)（結果に誰が解いたかを含める）、[0021](0021-subject-config-split.md)（被験構成）、[0023](0023-grader-interface.md)（採点器の入出力）、[0034](0034-sample-id-naming.md)（サンプルID）、[0050](0050-trace-as-jsonl.md)（トレース）、[0059](0059-grades-and-diagnosis-in-separate-files.md)（成績と診断のファイル）
- 採点の段階：全体。段階0〜2の結果を、どこに置くか

## 背景

- 1回の実行は、1つの被験構成が、1つのサンプルを、1回解くことである。実行ごとに、結果のフォルダ（`results/<run_id>/`）を作り、実行記録・トレース・答案・成績・診断を置く（[0050](0050-trace-as-jsonl.md)、[0059](0059-grades-and-diagnosis-in-separate-files.md)）。
- `run_id` は「実行ごとの一意なID」と決めたが、付け方は決めていなかった（[0018](0018-results-include-subject-info.md)、TODO 10章）。[0018](0018-results-include-subject-info.md) の例（日時・被験構成・何回目か）には、サンプルもタスクも入っていない。`run_id` を見ても、何の実行か分からない。
- `sample_id` は、タスクの中でしか一意でない。サンプルはタスクのフォルダの中に置き（[0016](0016-task-folder-per-task.md)）、IDにタスクを入れないためである（[0034](0034-sample-id-naming.md)）。同じ買取表を別のタスクで使えば、同じ `sample_id` になりうる。
- 同じ被験構成で、同じサンプルを、測り直すことがある。実行スクリプトの不具合を直したあと、モデルが更新されたあと、devとtestで別のサンプルを測るとき、などである。繰り返し（`repeat`）は、ばらつきを見るための番号である。番号を続けて測り直しを表すと、どの結果が1つにまとまるかが分からなくなる。

| 日 | 出来事 | `repeat` の番号を続ける | 測定でまとめる |
|---|---|---|---|
| 11/10 | `qwen-h0` を3回ずつ実行。あとで、実行スクリプトの不具合が分かる | `r1`・`r2`・`r3` | 1つ目の測定の `r1`〜`r3` |
| 11/12 | 不具合を直して、測り直す | `r4`・`r5`・`r6` | 2つ目の測定の `r1`〜`r3` |
| 集計するとき | どれをまとめるか | 全部まとめると、不具合のある結果が混ざる。使う番号を、別に書いておく必要がある | 測定を1つ選べば済む |

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 1つの名前にする（例：`<タスク>_<サンプル>_<被験構成>_r<繰り返し>`） | どこにでも1つの文字列で書ける | 長い。区切りの文字が、IDの中の文字（ハイフン）とぶつかる。まとまりで探しにくい |
| B. 階層にし、サンプルを被験構成より上にする | 同じサンプルでの、被験構成どうしの見比べが、1つのフォルダで済む | 1回の測定が、サンプルの数だけのフォルダに散らばる |
| **C. 階層にし、被験構成をサンプルより上にする** | 1回の測定が、1つのフォルダに収まる。被験構成ごとに、サンプルの成績が並ぶ | 同じサンプルでの見比べは、レポートで並べ直す |

## 決定

**C にする。** 結果は、次の階層に置く。

```
results/<タスク>/<被験構成>/<測定>/<サンプル>/r<繰り返し>/
├── run.yaml        実行記録
├── trace.jsonl     トレース
├── output.json     答案
├── metrics.json    成績
└── diagnosis.json  診断
```

| 階層 | 中身 | 例 |
|---|---|---|
| タスク | タスク | `buylist-card-id` |
| 被験構成 | 被験構成の名前（[0021](0021-subject-config-split.md)） | `qwen-h0` |
| 測定 | 同じ被験構成を、同じ条件で、決めたサンプルと繰り返しの回数だけ、まとめて実行したもの | 名前の付け方は、まだ決めていない（下） |
| サンプル | `sample_id`（[0034](0034-sample-id-naming.md)） | `magi-nagoya-20261030` |
| 繰り返し | 1回の測定の中で、同じサンプルを何回目に解いたか（1〜被験構成の `repeats`） | `r1` |

- `run_id` は、`results/` の下の道すじにする。例：`buylist-card-id/qwen-h0/<測定>/magi-nagoya-20261030/r1`
- 名前は人が読むため、中の項目は機械が読むため、と分ける。`run.yaml`・`metrics.json`・`diagnosis.json` の中にも、タスク・被験構成・測定・`sample_id`・`repeat` を項目として書く。採点器やレポートは、`run_id` を分解して読まない。
- `summarize` は、1つの被験構成の、1回の測定ごとに、`summary.json` を作る。[0023](0023-grader-interface.md) の「1つの被験構成の、すべての `metrics.json`」は、この決定で「1つの被験構成の、1回の測定の、すべての `metrics.json`」に置き換わる。
- 測定を何で区別し、どう名付けるかは、まだ決めていない（TODO 10章）。

### 例：devのサンプルで改善し、testのサンプルで確かめる

サンプルA（`magi-nagoya-20261030`）がdev、サンプルB（`torekingu-akiba-20261025`）がtestのとき（測定の名前は仮）：

```
results/buylist-card-id/
├── qwen-h0/
│   └── <測定1>/                       ← devのAで測る
│       └── magi-nagoya-20261030/ r1, r2, r3
└── qwen-h1/
    ├── <測定1>/                       ← devのAで測る
    │   └── magi-nagoya-20261030/ r1, r2, r3
    └── <測定2>/                       ← testのBで確かめる
        └── torekingu-akiba-20261025/ r1, r2, r3
```

被験構成ごとに、どのサンプルでどうだったかが並ぶ。改善した被験構成を別のサンプルで確かめるときは、同じ被験構成の下に、測定を1つ足す。

## 理由

試験に見立てると、生徒（被験構成）ごとのファイルを作り、その中に、模試（測定）ごとの答案（サンプル・何回目か）をとじる形である。

| | A. 1つの名前 | B. サンプルが上 | **C. 被験構成が上** |
|---|---|---|---|
| 名前から、何の実行か分かるか | 分かる（区切りに注意が要る） | 分かる | 分かる |
| 1回の測定が、どこにあるか | 名前で探す | サンプルの数だけのフォルダに散らばる | 1つのフォルダ |
| 被験構成ごとに、サンプルの成績を見られるか | 名前で探す | フォルダをまたいで集める | 1つのフォルダの下に並ぶ |
| 同じサンプルで、被験構成どうしを見比べられるか | 名前で探す | 1つのフォルダの下に並ぶ | レポートで並べ直す |

- **被験構成ごとに、サンプルの成績が並ぶため。** 比べる単位は被験構成である（`summary.json`、比較表の1行。[0023](0023-grader-interface.md)）。被験構成を上にすれば、被験構成ごとに、どのサンプルでどうだったかが分かり、どの被験構成が良いかを比べやすい。B を選ばなかったのはこのため。
- **1回の測定を、1つのフォルダに収めるため。** 1回の測定は、ふつう何枚ものサンプルにまたがる（M0で1〜3枚、M2では10枚以上をdevとtestに分ける）。B では、1回の測定が、サンプルの数だけのフォルダに散らばる。C なら、`summarize` は1つのフォルダの下をまとめるだけで済み、失敗した測定を外すのもフォルダ1つで済む。
- **devで改善した被験構成を、testで確かめる場面も表せるため。** 同じ被験構成の下に、testのサンプルの測定を足すだけである。
- **名前ではなく階層にするため。** 大きいまとまりから順に並べれば、住所のように、どこを見ればよいかが分かる。区切りの文字が、IDの中の文字とぶつかることもない。A を選ばなかったのはこのため。
- **タスクを入れるため。** `sample_id` は、タスクの中でしか一意でない。
- **測定を入れるため。** 繰り返しは、ばらつきを見るための番号で、測り直しを区別するものではない。条件の違う結果が、1つのばらつきの計算に混ざらないように、測定でまとめる。
- **中の項目にも書くため。** 名前の付け方を変えても、採点器やレポートが壊れない。
- **同じサンプルでの見比べは、レポートで並べ直せるため。** 中の項目（`sample_id` など）を読めばよいので、フォルダの順には縛られない。
