# 0032. 決まりの本文はそれだけで読めるように書き、出典（see）はLLMに渡さない

- ステータス：採用
- 日付：2026-10-29
- 決定者：kajiwara
- 関係するADR：[0030](0030-task-spec-in-yaml.md)（タスクの仕様はYAML）、[0031](0031-schema-kind-and-file-format.md)（ファイルの書き方は読み手に合わせる）

## 背景

- 決まりを番号付きの一覧で書くファイルが2つある。
  - `spec.yaml`：タスクの仕様。被験ハーネスが、これをもとにプロンプトを書き、モデルに伝える（[0030](0030-task-spec-in-yaml.md)）。
  - `gold-guideline.yaml`：正解データの作り方。人が使うほか、下書きを作るLLMにも渡す。
- どちらの決まりにも、ADRや設計書を指す `see` を付けている。しかし、LLMはADRや設計書をたどれない。
- ADRや設計書をまとめてLLMに渡すと、コンテキストが埋まり、費用も増える。関係のない情報で、判断がぶれる原因にもなる。これは、ドキュメントをどこに置くか（リポジトリ、S3など）に関係なく起きる。問題は置き場所ではなく、LLMに何を渡すか。
- `gold-guideline.yaml` には、下書きのLLMには関係のない決まり（記録の付け方、スキーマに値を足す作業など）も入っている。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 参照先のドキュメントも、まとめてLLMに渡す | 決まりの背景まで伝わる | コンテキストが埋まり、費用が増える。関係のない情報で判断がぶれる |
| B. 必要なドキュメントを、LLMが自分で取りに行けるようにする（S3に置いて、取得の道具を渡すなど） | 必要なときだけ読める | 取りに行くかどうか、何を読むかがLLM任せになり、結果が揺れる。仕組みも要る |
| **C. 決まりの本文だけで作業できるように書き、`see` は人のための出典としてLLMに渡さない。誰に渡す決まりかも明示する** | 渡す量が小さく、揺れない。置き場所に左右されない | 本文を自己完結させる手間がかかる。背景はLLMに伝わらない（短い `why` で補う） |

## 決定

**C にする。**

- **決まりの本文（`text`、`examples`）は、それだけで読めるように書く。** 「ADR-0027 のとおり」「R-01 と同じく」のように、ほかのドキュメントや決まりを読まないとわからない書き方はしない。
- **`see` は、人がなぜそう決めたかをたどるための出典とする。LLMには渡さない。**
- **`why`（理由）は短く書き、LLMに渡してよい。** 迷ったときの判断の助けになるため。`why` の中にも、ドキュメントへの参照は書かない（参照は `see` に書く）。
- **誰に渡す決まりかを、`for` の欄で明示する**（`gold-guideline.yaml`）。
  - `draft`：下書きを作るLLMにも渡す。
  - `verify`：下書きを確かめる人が使う。
  - 下書きのときは、`draft` の決まりの `text`・`examples`・`why` だけを取り出して渡す。
- **`gold-guideline.yaml` は、被験エージェントには渡さない。** 正解の作り方が漏れると、評価が成り立たなくなるため。

## 理由

- **LLMに渡す量を小さく、決まったものにするため。** 本文が自己完結していれば、ドキュメントを渡す必要がない。A を選ばなかったのは、コンテキストと費用を使い、関係のない情報で判断がぶれるため。
- **結果を揺らさないため。** LLMが自分でドキュメントを取りに行く形では、何を読むかで結果が変わる。評価や正解データの下書きでは、同じ入力から同じように動いてほしい。B を選ばなかったのはこのため。
- **ドキュメントの置き場所と切り離すため。** 渡すものが決まりの本文だけなら、ADRや設計書をリポジトリに置いても、S3に置いても、LLMの側は変わらない。置き場所は、インフラの設計で別に決められる。
- **出典は、人には必要なため。** なぜその決まりにしたかは、あとで決まりを見直すときに要る。`see` を消すのではなく、人のための欄として残す。
- **`for` で渡す相手を分けるのは、** 下書きのLLMに、人の作業の決まり（記録、確認、修正）を渡しても役に立たず、判断がぶれる原因になるため。

## 影響

- `spec.yaml` と `gold-guideline.yaml` の先頭に、この決まりを書く。
- `gold-guideline.yaml` の決まりに `for` の欄を足し、本文と `why` から、ドキュメントへの参照を外す。
- 被験ハーネスのプロンプト（TODO 9章）を書くときは、`spec.yaml` の `text`・`examples` をもとにし、`see` は使わない。
- 正解データの下書き（TODO 8章）では、`gold-guideline.yaml` の `draft` の決まりだけを渡す。取り出す道具を作るかは、そのときに決める。
- 見直すきっかけ：決まりの本文だけでは、LLMが正しく作業できないことがわかったとき。
