# 0030. タスクの仕様はYAMLで書き、モデルへの伝え方は被験ハーネスのプロンプトが受け持つ（0016の一部を置き換え）

- ステータス：採用
- 日付：2026-10-29
- 決定者：kajiwara
- 関係するADR：[0016](0016-task-folder-per-task.md)（タスクごとのフォルダ）、[0021](0021-subject-config-split.md)（被験エージェントの設定を3つに分ける）、[0022](0022-harness-level-and-components.md)（被験ハーネスの段階と部品の組み合わせ）、[0027](0027-provisional-key-variant.md)（仕様の軸）

## 背景

- タスクの仕様（何を求めるか）は、[0016](0016-task-folder-per-task.md) で `tasks/<タスク名>/spec.md` に置くと決めた。説明は「被験エージェントに渡す説明」で、Markdownの文をそのままモデルに渡すように読める。
- 一方で、モデルに **どう伝えるか**（プロンプトの文、順番、例の付け方）は、被験ハーネスの設計の一部である（[0021](0021-subject-config-split.md)、[0022](0022-harness-level-and-components.md)）。伝え方を変えて成績がどう変わるかは、このプロジェクトで測りたいことそのもの（第一の目的）。
- タスクの仕様をモデルに渡す文として書くと、伝え方がタスクの側で1つに固定される。
  - どのハーネスも同じ文を渡すことになり、伝え方の違いを試せない。
  - 伝え方を変えたくて仕様を書き換えると、物差しが変わる。成績の差が、ハーネスの改善によるものか、タスクが変わったせいか、区別できなくなる。
- タスクの仕様には、機械でも使いたい情報がある。
  - 仕様の軸の値（[0027](0027-provisional-key-variant.md)）や `status` の値は、仕様・出力のスキーマ・採点器の3か所で使う。別々に書くと、いずれずれる。
  - 失敗の分析で「どの決まりが守られなかったか」を数えるには、決まりを指し示す番号が要る。
- なお、書式をYAMLにしても、モデルの出力の揺れはあまり減らない。揺れの主な原因は、決まりのあいまいさと出力の自由さで、これは出力のスキーマ（値の一覧）と、決まりに付ける例で減らす。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. Markdown（`spec.md`）をモデルに渡す文として書く（今の決定） | 人が読みやすい。書くのが速い | 伝え方がタスクの側に固定される。値の一覧がスキーマや採点器とずれても気づけない。決まりを番号で指せない |
| B. Markdownで書き、モデルに渡す文は別に書く | 伝え方を分けられる | 決まりが文の中に埋もれ、機械で扱えない。値の一覧のずれに気づけない |
| **C. YAML（`spec.yaml`）で、決まりを番号付きの項目の一覧として書く。モデルに渡す文は、被験ハーネスのプロンプトが書く** | 伝え方を分けられる。決まりを番号で指せる。値の一覧はスキーマを参照し、ずれを機械で見つけられる | 決まりの文は日本語のまま。読みやすさはMarkdownに少し劣る |

## 決定

**C にする。**

- タスクの仕様は `tasks/<タスク名>/spec.yaml` に書く。[0016](0016-task-folder-per-task.md) の `spec.md` を置き換える。`task.yaml` の `spec` も `spec.yaml` にする。
- `spec.yaml` は **何を求めるか** だけを持つ。決まりは、番号（`R-01` など）・文・例の一覧にする。
- **値の一覧は、出力のスキーマ（`output.schema.json`）だけが持つ。** `spec.yaml` は、スキーマの場所を指して参照する。
- **モデルにどう伝えるかは、被験ハーネスのプロンプト（`subject/<タスク名>/<被験ハーネスの名前>/prompt.md`）が受け持つ。** プロンプトは `spec.yaml` の決まりをもとに書くが、文・順番・例の付け方は自由に変えてよい。
- 向きは一方向にする。被験ハーネスは `spec.yaml` を読むが、書き換えない。`spec.yaml` は被験ハーネスの中身を知らない。
- プロンプトのファイルは、M0ではMarkdown（`prompt.md`）のままにする。中身がモデルに渡す文そのものだから。決まりをYAMLの形でモデルに見せると良くなるかは、あとでプロンプトの種類（[0022](0022-harness-level-and-components.md) の `prompt.variant`）を変えて試す。

```yaml
# tasks/buylist-card-id/spec.yaml（抜粋）
id: buylist-card-id
version: 1
output:
  schema: schemas/output.schema.json
rules:
  - id: R-01
    text: 位置は、上から1始まりの段、左から1始まりの列で数える。
  - id: R-09
    text: 版・加工・スタンプは、画像で確かめられない軸を「指定なし」にする。
```

## 理由

- **物差しと測る対象を、別のファイルに分けるため。** `spec.yaml` は物差しで、変えない。プロンプトは測る対象で、変えて効果を見る。分けておけば、成績の差を伝え方の差として読める。A を選ばなかったのはこのため。
- **決まりを番号で指せるようにするため。** 失敗の分類（設計書 9.2）で「R-04（カード名は画像の通り）が守られなかった」のように数えられる。プロンプトを書くときも、どの決まりを伝えたかを番号で確かめられる。
- **値の一覧を1か所にまとめるため。** 仕様の軸の値などをスキーマだけに書き、`spec.yaml` と採点器はそれを参照する。値を足したときに、どこかを直し忘れることがなくなる。B を選ばなかったのは、決まりも値も文の中に埋もれ、機械で扱えないため。
- **正解データの列の定義（[0019](0019-gold-schema-machine-readable.md)）と扱いを揃えるため。** タスクの中身のうち、機械でも使うものは、機械で読める形にしている。
- **プロンプトをMarkdownのままにするのは、** モデルが受け取る文と、ファイルの中身を同じにしておきたいため。ファイルの形と、モデルに見せる文の形は別々に決められるので、YAML風の見せ方を試すこともできる。

## 決めるために必要なこと

- **プロンプトに決まりをどう入れるか。** 案1：プロンプトの作り手が `spec.yaml` を読んで、手で書く（伝え方の自由が一番大きいが、決まりの書き漏れが起きうる）。案2：プロンプトに差し込み場所を作り、実行スクリプトが `spec.yaml` の決まりを差し込む（書き漏れはないが、差し込むときの書き方が評価する側に固定される）。M0のH0では、どちらにするか。
- **書き漏れをどう確かめるか。** 案：プロンプトの中で、どの決まりを伝えたかを番号で書いておき、`spec.yaml` の番号と突き合わせる。
