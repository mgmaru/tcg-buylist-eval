# 0061. 被験構成は「比べて選びたいもの」、測定条件は「比べるときにそろえたいもの」とし、測定条件もファイルで定義する（0021の一部を置き換え）

- ステータス：採用
- 日付：2026-11-04
- 決定者：kajiwara
- 関係するADR：[0004](0004-infrastructure-as-code.md)（インフラをコードで作る）、[0018](0018-results-include-subject-info.md)（結果に誰が解いたかを含める）、[0021](0021-subject-config-split.md)（モデル・被験ハーネス・被験構成）、[0022](0022-harness-level-and-components.md)（被験ハーネスの段階と部品）、[0023](0023-grader-interface.md)（採点器の入出力）、[0041](0041-format-error-kinds-and-units.md)（形式の誤り）、[0060](0060-results-folder-by-config-conditions-sample.md)（結果の置き場所）、[0062](0062-roles-question-setter-and-administrator.md)（評価する側の役）

## 背景

- 結果のフォルダに、測定条件の階層を置く（[0060](0060-results-folder-by-config-conditions-sample.md)）。測定条件とは何かを、被験構成と分けて決める必要がある。
- 被験構成（`configs/<構成名>.yaml`）には、モデル・被験ハーネス・制限（時間制限）・繰り返しの回数を書くと決めていた（[0021](0021-subject-config-split.md)）。実行の環境（どの機械で、どの推論サーバーの版で、どの実行スクリプトの版で動かしたか）には、決まった書き場所がなかった。実行記録に、実行1回ずつ残すだけだった（設計書 5.5）。
- 被験構成は、比べる相手である。比べる相手でないものまで被験構成に入れると、環境が変わるたびに別の被験構成になり、何を比べているのかが分からなくなる。逆に、そろえるべきものが被験構成ごとにばらばらだと、公平に比べられない。
- 別の場所で同じ測定を作り直すには、何を、どんな条件で測ったかが、ファイルで決まっている必要がある。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 今のまま。被験構成に繰り返しの回数まで書き、実行の環境は実行記録にだけ残す | 変更が少ない | 被験構成ごとに繰り返しの回数を変えられ、公平に比べられない。実行の環境が変わっても、結果が分かれない。別の場所で作り直すための定義がない |
| B. 実行の環境も、すべて被験構成に書く | ファイルが1つで済む | 環境が変わるたびに別の被験構成になり、比べる相手が増える。被験構成の名前が、評価したいものを表さなくなる |
| **C. 比べて選びたいものは被験構成に、比べるときにそろえたいものは測定条件に分け、測定条件もファイルで定義する** | 被験構成は、評価したいものだけを表す。測定条件をそろえれば公平に比べられ、ファイルを持っていけば別の場所で作り直せる | ファイルが1つ増える。境目に迷う項目がある |

## 決定

**C にする。**

| | 被験構成 | 測定条件 |
|---|---|---|
| 基準 | 比べて、選びたいもの（わざと変える） | 比べるときに、そろえたいもの（ふつうは変えない。変わったら、別の測定条件にする） |
| 定義のファイル | `configs/<構成名>.yaml`。モデルの設定と被験ハーネスを指す（[0021](0021-subject-config-split.md)） | `conditions/<条件名>.yaml` |
| 決める役 | 被験エージェントを作る人（[0062](0062-roles-question-setter-and-administrator.md)） | 実施者（[0062](0062-roles-question-setter-and-administrator.md)） |

項目は、次のように振り分ける。

| 項目 | どちらか | 理由 |
|---|---|---|
| モデル（量子化を含む） | 被験構成 | 比べて選ぶもの |
| モデルの設定（思考、温度、コンテキスト長） | 被験構成 | ふるまいを変えるので、比べて選ぶもの。[0021](0021-subject-config-split.md) の例のとおり、モデルの設定のファイルに書く |
| 被験ハーネス（プロンプト、ツール、部品） | 被験構成 | 比べて選ぶもの（[0022](0022-harness-level-and-components.md)） |
| 時間制限 | 被験構成 | 被験構成ごとの、安全のための打ち切り。速さは所要時間として、別に測る |
| 実行の環境（どの機械、OSのイメージ、クラウドのAPI） | 測定条件 | そろえたいもの |
| 推論サーバー（Ollamaなど）の版 | 測定条件 | そろえたいもの |
| 実行スクリプトの版 | 測定条件 | そろえたいもの。不具合を直したら、別の測定条件になる |
| 繰り返しの回数 | 測定条件 | 同じ回数で比べてこそ、正解率やばらつきを公平に比べられる |
| カードDBの版（M1から） | 測定条件 | 同じ時期に比べる被験構成どうしで、そろえたいもの |

- 採点の条件（採点器の版、正解データの版）は、どちらにも入れない。実行し直さずに、採点だけやり直せるためである。これまでどおり、`metrics.json` に書く（[0023](0023-grader-interface.md)）。
- [0021](0021-subject-config-split.md) の「被験構成に、繰り返しの回数を書く」は、この決定で「測定条件に書く」に置き換わる。時間制限は、[0021](0021-subject-config-split.md) のとおり被験構成に書く。
- 繰り返しの回数を変えたら、別の測定条件にする。回数の違う測定どうしは、同じ物差しで比べられないためである。
- 測定条件の定義は、リポジトリの `conditions/<条件名>.yaml` に置く。実行スクリプトは、実際に使った定義の写しを、結果のフォルダの測定条件の階層に置く（[0060](0060-results-folder-by-config-conditions-sample.md)）。あとで定義のファイルを直しても、そのとき何で測ったかが残る。
- 実行の環境は、インフラのコードで作る（[0004](0004-infrastructure-as-code.md)）。測定条件のファイルには、どの版のインフラのコードで作った環境かも書く。
- 測定条件のファイルの項目の名前と、条件名の付け方は、まだ決めていない（TODO 10章）。

## 理由

試験に見立てると、被験構成は受験者で、測定条件は試験会場と決まり（机、時計、受けられる回数）である。受験者は比べたいもので、会場はそろえたいものである。会場の様子を記録しておけば、別の場所で同じ会場を作り直せる。

| | A. 今のまま | B. すべて被験構成 | **C. 分ける** |
|---|---|---|---|
| 被験構成が、評価したいものだけを表すか | 表す | 表さない（環境まで入る） | 表す |
| 公平に比べられるか（繰り返しの回数などがそろうか） | そろわない | そろう | そろう |
| 条件が変わったとき、結果が分かれるか | 分かれない | 分かれる（別の被験構成として） | 分かれる（別の測定条件として） |
| 別の場所で作り直せるか | 作り直せない | 作り直せる | 作り直せる |

- **被験構成を、評価したいものだけにするため。** 実行の環境まで被験構成に入れると、環境が変わるたびに比べる相手が増え、被験構成の名前が何を評価しているのかを表さなくなる。B を選ばなかったのはこのため。
- **公平に比べるため。** 繰り返しの回数が被験構成ごとに違うと、同じ物差しで比べられない。同じ回数で、より正解率が高いほうが良い被験構成だと言えるようにする。A を選ばなかったのはこのため。
- **時間制限は、被験構成に残すため。** 重いモデルは、応答に時間がかかる。時間制限をそろえると、遅いだけの被験構成が時間切れになる。時間切れは「読めない」（形式の誤り）になり、そのサンプルの全カードが保留になる（[0041](0041-format-error-kinds-and-units.md)）。遅いことが、形式を守れないことに見えてしまう。速さは、所要時間として別に測る。
- **別の場所で作り直すため。** 被験構成と測定条件の両方がファイルで決まっていれば、それを持っていけば、同じ測定を作り直せる。
- **採点の条件を入れないため。** 採点器や正解データを直したときは、実行し直さずに、採点だけやり直せる。測定条件に入れると、採点し直すたびに、別の測定条件の結果に見えてしまう。
