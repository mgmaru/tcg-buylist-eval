# 0062. 評価する側に、作問者と実施者の役を置き、評価用ハーネスは決まったことを読んで行うだけにする

- ステータス：採用
- 日付：2026-11-04
- 決定者：kajiwara
- 関係するADR：[0016](0016-task-folder-per-task.md)（タスクごとのフォルダ）、[0021](0021-subject-config-split.md)（モデル・被験ハーネス・被験構成）、[0030](0030-task-spec-in-yaml.md)（タスクの仕様）、[0032](0032-separate-files-by-reader.md)（読み手ごとのファイル）、[0049](0049-subject-gets-answering-instructions-only.md)（被験エージェントには回答の仕方だけを伝える）、[0061](0061-subject-config-and-measurement-conditions.md)（被験構成と測定条件）

## 背景

- 設計書 1.3 は、評価する側（評価用ハーネス：実行スクリプト、採点器、レポート）と、評価される側（被験ハーネス）の2つに分けている。
- しかし、タスク（仕様・サンプル・正解データ）を作る人と、測定条件（[0061](0061-subject-config-and-measurement-conditions.md)）を決める人が、どちらの側の、どんな役なのかを決めていなかった。
- 測定条件を、被験エージェントを作る人が変えられると、自分の被験構成に有利な条件にできてしまう。
- 試験に見立てると、受験者（被験エージェント）と採点者（採点器）のほかに、問題と模範解答を作る人（作問者）と、試験の会場・決まり・回数を決める人（実施者）がいる。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 評価用ハーネスの責務にする（決める役を立てない） | 役が増えない | 仕組み（コード）と、決めること（何を、どんな条件で測るか）の区別が、あいまいになる |
| B. 1つの役（出題者）が、タスクと測定条件の両方を決める | 役が少なく、分かりやすい | 中身の違うもの（タスクごとの問題と、タスクをまたぐ実行の環境）を、同じ役が持つ |
| **C. 作問者と実施者の2つの役を置く** | 範囲も変わる時期も違うものを、分けて持てる | 役が1つ増える |

## 決定

**C にする。** 役を、次のように分ける。

| 役 | 側 | 試験でいうと | 決めること・作るもの | ファイル |
|---|---|---|---|---|
| 作問者 | 評価する側 | 問題と模範解答を作る | タスクの仕様、出力のスキーマ、サンプル、正解データ | `tasks/<タスク>/`（[0016](0016-task-folder-per-task.md)、[0030](0030-task-spec-in-yaml.md)） |
| 実施者 | 評価する側 | 試験の会場・決まり・回数を決める | 測定条件（実行の環境、推論サーバーと実行スクリプトの版、繰り返しの回数 など） | `conditions/<条件名>.yaml`（[0061](0061-subject-config-and-measurement-conditions.md)） |
| 評価用ハーネス | 評価する側 | 試験監督と採点者 | 実行、採点、集計、レポート | 実行スクリプト、採点器、レポートのコード |
| 被験エージェントを作る人 | 評価される側 | 受験者を育てる | 被験構成、被験ハーネス、モデルの設定 | `configs/`、`subject/`、`models/`（[0021](0021-subject-config-split.md)） |
| 被験エージェント | 評価される側 | 受験者 | 答案 | `output.json` |

- 評価用ハーネスの仕組み（コード）は、何を、どんな条件で測るかを持たない。作問者と実施者が決めたことを、ファイルから読んで行うだけにする。
- 被験エージェントを作る人は、被験ハーネスを直すときに、タスクと測定条件のファイルを変えない。
- 今は、同じ人がすべての役を受け持つ。それでも、ファイルと決まりのうえで、役を分ける。

## 理由

| | A. 評価用ハーネスの責務 | B. 1つの役 | **C. 2つの役** |
|---|---|---|---|
| 決めることと、仕組みが分かれるか | 分かれない | 分かれる | 分かれる |
| 被験エージェントを作る人から、測定条件を守れるか | あいまい | 守れる | 守れる |
| 範囲や変わる時期の違うものを、分けて持てるか | ― | 分けられない | 分けられる |

- **公平に比べるため。** 測定条件を決めるのは、評価する側にする。被験エージェントを作る人が、自分の被験構成に有利なように条件を変えられないようにする。被験エージェントに採点の仕組みを伝えない（[0049](0049-subject-gets-answering-instructions-only.md)）のと同じ考え方である。
- **決めることを、仕組みから分けるため。** 何を、どんな条件で測るかをファイルに書き、評価用ハーネスはそれを読むだけにすれば、タスクや条件を変えても、コードを直さずに済む。タスクは、もうこの形になっている（タスクの差し込み口。[0016](0016-task-folder-per-task.md)、[0030](0030-task-spec-in-yaml.md)）。測定条件も同じ形にする。A を選ばなかったのはこのため。
- **範囲と、変わる時期が違うため。** 作問は、タスクごとで、サンプルを足すたびに変わる。実施は、実行の環境（インフラ）や実行スクリプトが変わるたびに変わり、タスクをまたいで同じ測定条件を使うこともある。B を選ばなかったのはこのため。
- **devとtestの目的を守るため。** 被験ハーネスを直す人が、タスクや測定条件に触らなければ、testのサンプルに合わせ込むことを防げる（設計書 10.3）。

## 影響

- 設計書 1.3 に、役の表を足す。設計書 4章に、どのフォルダをどの役が持つかを書く。
- 合格ライン（今は `task.yaml` の `pass`）を、作問者と実施者のどちらが決めるかを決める（TODO 10章）。
- 被験ハーネスを直すPRで、`tasks/` と `conditions/` を変えていないかを確かめる（TODO 9章の、PRでのレビュー）。
