# 0060. 結果は、タスク・被験構成・測定条件・サンプル・繰り返しの順の階層に置き、run_id はその道すじにする（0023の一部を置き換え）

- 日付：2026-11-04
- 決定者：kajiwara
- 関係するADR：[0016](0016-task-folder-per-task.md)（タスクごとのフォルダ）、[0018](0018-results-include-subject-info.md)（結果に誰が解いたかを含める）、[0021](0021-subject-config-split.md)（被験構成）、[0023](0023-grader-interface.md)（採点器の入出力）、[0034](0034-sample-id-naming.md)（サンプルID）、[0050](0050-trace-as-jsonl.md)（トレース）、[0059](0059-grades-and-diagnosis-in-separate-files.md)（成績と診断のファイル）、[0061](0061-subject-config-and-measurement-conditions.md)（被験構成と測定条件）、[0062](0062-roles-question-setter-and-administrator.md)（評価する側の役）
- 採点の段階：全体。段階0〜2の結果を、どこに置くか

## 背景

- 1回の実行は、1つの被験構成が、1つのサンプルを、1回解くことである。実行ごとに、結果のフォルダ（`results/<run_id>/`）を作り、実行記録・トレース・答案・成績・診断を置く（[0050](0050-trace-as-jsonl.md)、[0059](0059-grades-and-diagnosis-in-separate-files.md)）。
- `run_id` は「実行ごとの一意なID」と決めたが、付け方は決めていなかった（[0018](0018-results-include-subject-info.md)、TODO 10章）。[0018](0018-results-include-subject-info.md) の例（日時・被験構成・何回目か）には、サンプルもタスクも入っていない。`run_id` を見ても、何の実行か分からない。
- `sample_id` は、タスクの中でしか一意でない。サンプルはタスクのフォルダの中に置き（[0016](0016-task-folder-per-task.md)）、IDにタスクを入れないためである（[0034](0034-sample-id-naming.md)）。同じ買取表を別のタスクで使えば、同じ `sample_id` になりうる。
- 同じ被験構成で、同じサンプルを、条件を変えて測り直すことがある。実行スクリプトの不具合を直したあと、推論サーバーの版を上げたあと、などである。繰り返し（`repeat`）は、ばらつきを見るための番号で、測り直しを区別するものではない。番号を続けて測り直しを表すと、条件の違う結果が、1つのばらつきの計算に混ざる。
- 測り直しを区別するために、ほかに次の名前も考えた。どれも、区別したいもの（どんな条件で測ったか）を表していなかった。

| 考えた名前 | 例 | 合わなかった点 |
|---|---|---|
| 開始日時 | `20261110-1000` | いつ測ったかは、評価の上で意味がない。名前を見ても、どの結果どうしを比べてよいかが分からない |
| 測定の通し番号 | `m1`、`m2` | 何回目かは分かるが、何が違うのかが分からない |
| サンプルの集まりと何回目か | `dev-1` | どのサンプルを測ったかを、次の階層（サンプル）と二重に書くことになる |

- 区別したいのは、どんな条件で測ったか（測定条件）である。測定条件は、被験構成と分けてファイルで定義する（[0061](0061-subject-config-and-measurement-conditions.md)）。

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 1つの名前にする（例：`<タスク>_<サンプル>_<被験構成>_r<繰り返し>`） | どこにでも1つの文字列で書ける | 長い。区切りの文字が、IDの中の文字（ハイフン）とぶつかる。まとまりで探しにくい。測り直しを区別できない |
| B. 階層にし、サンプルを被験構成より上にする | 同じサンプルでの、被験構成どうしの見比べが、1つのフォルダで済む | 1つの測定条件での結果が、サンプルの数だけのフォルダに散らばる |
| **C. 階層にし、被験構成をサンプルより上にし、その間に測定条件を置く** | 被験構成ごとに、サンプルの成績が並ぶ。1つの測定条件での結果が、1つのフォルダに収まる。条件が変われば、別のフォルダになる | 同じサンプルでの見比べは、レポートで並べ直す |

## 決定

**C にする。** 結果は、次の階層に置く。

```
results/<タスク>/<被験構成>/<測定条件>/
├── conditions.yaml          測定条件の写し（実際に使った定義。0061）
└── <サンプル>/r<繰り返し>/
    ├── run.yaml             実行記録
    ├── trace.jsonl          トレース
    ├── output.json          答案
    ├── metrics.json         成績
    └── diagnosis.json       診断
```

| 階層 | 中身 | 例 |
|---|---|---|
| タスク | タスク | `buylist-card-id` |
| 被験構成 | 被験構成の名前（`configs/<構成名>.yaml`。[0021](0021-subject-config-split.md)） | `qwen-h0` |
| 測定条件 | 測定条件の名前（`conditions/<条件名>.yaml`。[0061](0061-subject-config-and-measurement-conditions.md)） | 名前の付け方は、まだ決めていない |
| サンプル | `sample_id`（[0034](0034-sample-id-naming.md)） | `magi-nagoya-20261030` |
| 繰り返し | 同じ測定条件で、同じサンプルを、何回目に解いたか（1〜測定条件の繰り返しの回数） | `r1` |

- `run_id` は、`results/` の下の道すじにする。例：`buylist-card-id/qwen-h0/<測定条件>/magi-nagoya-20261030/r1`
- 名前は人が読むため、中の項目は機械が読むため、と分ける。`run.yaml`・`metrics.json`・`diagnosis.json` の中にも、タスク・被験構成・測定条件・`sample_id`・`repeat` を項目として書く。採点器やレポートは、`run_id` を分解して読まない。
- `summarize` は、1つの被験構成の、1つの測定条件ごとに、`summary.json` を作る。[0023](0023-grader-interface.md) の「1つの被験構成の、すべての `metrics.json`」は、この決定で「1つの被験構成の、1つの測定条件の、すべての `metrics.json`」に置き換わる。
- 同じ測定条件で、devとtestの両方のサンプルを測れば、同じ測定条件のフォルダの下に、サンプルごとのフォルダが並ぶ。devとtestを分けて集計する方法は、M2でサンプルを分けるときに決める（TODO 10章）。

### 例：devのサンプルで改善し、testのサンプルで確かめ、条件を変えて測り直す

サンプルA（`magi-nagoya-20261030`）がdev、サンプルB（`torekingu-akiba-20261025`）がtestのとき（測定条件の名前は仮）：

```
results/buylist-card-id/
├── qwen-h0/
│   └── <条件1>/
│       ├── conditions.yaml
│       └── magi-nagoya-20261030/ r1, r2, r3        ← devのAで測る
└── qwen-h1/
    ├── <条件1>/
    │   ├── conditions.yaml
    │   ├── magi-nagoya-20261030/ r1, r2, r3        ← devのAで測る
    │   └── torekingu-akiba-20261025/ r1, r2, r3    ← testのBで確かめる
    └── <条件2>/                                     ← 実行スクリプトの不具合を直して、測り直した
        ├── conditions.yaml
        └── magi-nagoya-20261030/ r1, r2, r3
```

被験構成ごとに、どのサンプルでどうだったかが並ぶ。改善した被験構成を別のサンプルで確かめるときは、同じ測定条件のフォルダに、サンプルを足す。条件が変われば、別の測定条件のフォルダになり、前の結果も、どの条件だったかと一緒に残る。

## 理由

試験に見立てると、生徒（被験構成）ごとのファイルを作り、その中に、試験会場（測定条件）ごとの袋を入れ、袋の中に答案（サンプル・何回目か）を入れる形である。会場の様子は、袋に入れた会場の記録（`conditions.yaml`）に書く。

| | A. 1つの名前 | B. サンプルが上 | **C. 被験構成が上、その下に測定条件** |
|---|---|---|---|
| 名前から、何の実行か分かるか | 分かる（区切りに注意が要る） | 分かる | 分かる |
| 1つの測定条件での結果が、どこにあるか | 名前で探す | サンプルの数だけのフォルダに散らばる | 1つのフォルダ |
| 被験構成ごとに、サンプルの成績を見られるか | 名前で探す | フォルダをまたいで集める | 1つのフォルダの下に並ぶ |
| 条件を変えて測り直したとき | 区別できない | 区別できる | 区別できる。条件の記録と一緒に残る |
| 同じサンプルで、被験構成どうしを見比べられるか | 名前で探す | 1つのフォルダの下に並ぶ | レポートで並べ直す |

- **被験構成ごとに、サンプルの成績が並ぶため。** 比べる単位は被験構成である（`summary.json`、比較表の1行。[0023](0023-grader-interface.md)）。被験構成を上にすれば、被験構成ごとに、どのサンプルでどうだったかが分かり、どの被験構成が良いかを比べやすい。B を選ばなかったのはこのため。
- **1つの測定条件での結果を、1つのフォルダに収めるため。** 測定は、ふつう何枚ものサンプルにまたがる（M0で1〜3枚、M2では10枚以上をdevとtestに分ける）。C なら、`summarize` は1つのフォルダの下をまとめるだけで済み、失敗した測定を外すのもフォルダ1つで済む。
- **測り直しを、測定条件で区別するため。** 条件が変われば、別のフォルダになる。条件の違う結果が混ざらず、前の結果も残る。開始日時や通し番号と違って、名前の下にある記録（`conditions.yaml`）を見れば、何が違うのかが分かる。サンプルのことは書かないので、次の階層と二重にならない。
- **名前ではなく階層にするため。** 大きいまとまりから順に並べれば、住所のように、どこを見ればよいかが分かる。区切りの文字が、IDの中の文字とぶつかることもない。A を選ばなかったのはこのため。
- **タスクを入れるため。** `sample_id` は、タスクの中でしか一意でない。
- **中の項目にも書くため。** 名前の付け方を変えても、採点器やレポートが壊れない。
- **同じサンプルでの見比べは、レポートで並べ直せるため。** 中の項目（`sample_id` など）を読めばよいので、フォルダの順には縛られない。
