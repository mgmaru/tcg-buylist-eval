# 0032. ファイルは誰のための作業指示かで分け、LLMへの作業指示には、LLMの作業に必要なことだけを書く

- ステータス：採用
- 日付：2026-10-30
- 決定者：kajiwara
- 関係するADR：[0030](0030-task-spec-in-yaml.md)（タスクの仕様はYAML、伝え方はプロンプト）、[0031](0031-schema-kind-and-file-format.md)（ファイルの書き方は読み手に合わせる）

## 背景

- 正解データの作り方（`gold-guideline.yaml`）の最初の下書きは、1つのファイルに、人への作業指示（照合先の数、確認者の記録、版の上げ方など）と、下書きを作るLLMへの作業指示（カード名や番号の書き方など）が混ざっていた。決まりごとに、機械で確かめられるか（`check`）、誰に渡すか（`for`）の欄も付けていた。
- このファイルをLLMに丸ごと渡すと、LLMの作業に関係のない人向けの指示や出典もコンテキストに入る。
  - コンテキストが埋まり、APIの費用が増える。
  - LLMが、自分の作業ではない指示に迷う。
- 人にとっても、LLM向けの決まりと人向けの決まりが混ざっていて、読みにくい。
- 読み手で、これまでのファイルを振り返ると、次のようになっていた。

| ファイル | 読み手 | 状態 |
|---|---|---|
| `spec.yaml` | 人、被験ハーネス | よい。LLMに渡るのは、被験ハーネスの `prompt.md`（[0030](0030-task-spec-in-yaml.md)） |
| 被験ハーネスの `prompt.md` | LLM | よい。中身がそのまま渡る |
| `output.schema.json` | プログラム、LLM（モデルの呼び出しに渡す） | おおむねよい。ただし説明の文に、人向けの参照（決まりの番号、ADR）が入っていた |
| `gold.schema.yaml` | プログラム、人 | よい |
| `task.yaml` | プログラム、人 | よい |
| `gold-guideline.yaml` | 人、LLM | **読み手が混ざっていた** |

## 検討した選択肢

| 選択肢 | 良い点 | 弱い点 |
|---|---|---|
| A. 1つのファイルのまま、丸ごとLLMに渡す | ファイルが1つで済む | 人向けの指示や出典がコンテキストを埋め、費用が増える。LLMが迷う |
| B. 1つのファイルに、誰に渡すか（`for`）の欄を付け、LLM向けの決まりだけを取り出して渡す | ファイルが1つで済む。渡す量は小さい | 取り出す道具が要る。道具がなければ丸ごと渡しがちになる。LLMに何が渡ったかが、ファイルを見てもわからない。人にとっても読みにくいまま |
| **C. 誰のための作業指示かでファイルを分ける。LLMへの作業指示は専用のファイルにし、中身をそのまま渡す** | LLMに渡るものが、ファイルを見ればそのままわかる。渡す量を厳選できる。人のファイルも読みやすい | ファイルが増える。人のファイルとLLMのファイルの間で、内容がずれないように気をつける必要がある |

## 決定

**C にする。**

- **ファイルは、誰のための作業指示かで分ける。** 1つのファイルに、違う読み手への作業指示を混ぜない。
- **LLMへの作業指示は、専用のファイルにし、中身をそのまま渡す。** 取り出しや書き換えをせずに渡せる形にする。
- **LLMへの作業指示には、LLMが行う作業に必要なことだけを書く。** 人の作業、出典（ADRや設計書への参照）、確かめ方、ファイルの直し方などは書かない。ほかのファイルを読まないとわからない書き方もしない。
- **人のファイルからは、LLMのファイルやほかのファイルを指してよい。** 人はどのファイルも読めるため。逆向き（LLMのファイルから人のファイルを指す）はしない。
- **プログラムとLLMが読むファイル（`output.schema.json`）にも、人向けの参照や直し方のメモは書かない。**
- 正解データの作り方は、次の3つに分ける。

| ファイル | 読み手 | 中身 |
|---|---|---|
| `tasks/<タスク名>/gold-guideline.yaml` | 人 | 作業の手順（誰が行うかを `actor` で書く）と、人が確かめるときの決まり |
| `tasks/<タスク名>/gold-draft/prompt.md` | 下書きを作るLLM | 下書きの作業指示。列ごとの書き方と、出力の形 |
| `tasks/<タスク名>/schemas/gold.schema.yaml` | プログラム、人 | 各列の定義（何が正しい値か）と、機械で確かめる制約 |

- 被験エージェントの側と同じ作りにする。定義のファイルがあり、LLMへの作業指示は、それをLLM向けに書き直したものにする。

| | 定義 | LLMへの作業指示 |
|---|---|---|
| 被験エージェント | `spec.yaml` | 被験ハーネスの `prompt.md` |
| 正解データの下書き | `gold.schema.yaml` の各列の説明 | `gold-draft/prompt.md` |

## 理由

- **LLMに渡すコンテキストを厳選するため。** LLMの作業に関係のない情報は、コンテキストを埋めて費用を増やし、LLMを迷わせる。作業指示を読み手ごとに分ければ、LLMに渡るのは、その作業に必要なことだけになる。A を選ばなかったのはこのため。
- **LLMに何が渡ったかを、ファイルを見ればわかるようにするため。** 取り出して渡す形では、実際に渡った内容は、取り出す道具を通さないとわからない。中身をそのまま渡すファイルなら、レビューでも、そのまま確かめられる。B を選ばなかったのはこのため。取り出す道具を作る手間もかからない。
- **人のファイルも読みやすくするため。** 人のファイルは、人の作業の手順と確かめ方だけになり、LLM向けの細かい書き方や、機械で確かめる欄（`check`）が混ざらない。
- **被験エージェントの側と考え方をそろえるため。** [0030](0030-task-spec-in-yaml.md) で、タスクの仕様（定義）と、モデルへの伝え方（プロンプト）を分けた。正解データの下書きも同じ作りにすれば、どこに何があるかを迷わない。
- **機械で確かめることはスキーマに寄せるため。** 決まりごとに `check` を付けるより、確かめられる制約を `gold.schema.yaml` に書けば、プログラムがそのまま使える（[0031](0031-schema-kind-and-file-format.md) の、機械が読むもの・人が読むものの分け方とも合う）。

## 影響

- `gold-guideline.yaml` を、人への作業指示だけにする。手順に `actor`（`human`／`llm`／`tool`）を付け、決まりから `check` と `for` を外す。
- `gold-draft/prompt.md` を新しく作る。
- `gold.schema.yaml` の各列の説明を、正しい値の定義として書き直す（例も付ける）。照合先の数（`sources` は2つ以上）などの制約も足す。
- `output.schema.json` の説明の文から、人向けの参照（決まりの番号、ADR）と直し方のメモを外す。
- `spec.yaml` は、モデルには渡さない（渡るのは被験ハーネスの `prompt.md`）ことを、先頭に書く。
- **内容のずれに気をつける。** 定義（`gold.schema.yaml`、`spec.yaml`）を直したら、それを書き直したLLM向けのファイル（`gold-draft/prompt.md`、被験ハーネスの `prompt.md`）も確かめる。`gold-guideline.yaml` の G-09 に、この確認を書く。
- 見直すきっかけ：LLM向けのファイルと定義のずれが、たびたび起きるようになったとき。そのときは、定義からLLM向けのファイルを作る道具を考える。
