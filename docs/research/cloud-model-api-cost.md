# クラウドのモデルのAPI代の見積もり（Claude Opus 5.5）

調査日：2026-10-26

[ADR-0006](../adr/0006-cloud-model-authentication.md) の「M0の実行回数から、API代を見積もる」ための調査。クラウドのモデルは **Claude Opus 5.5**（モデルID `claude-opus-5-5`）とする。

## 結論

- Opus 5.5 の単価は、入力 4ドル／出力 20ドル（100万トークンあたり）。費用の大半は **出力**（思考のトークンと出力JSON）が占める。画像と指示文の入力は小さい。
- H0の1回は **約20〜90円**（標準で約45円）。
- **M0は約1,500〜3,000円** で収まる（試行を含めて30回程度）。月1万円の予算に入れても問題ない。
- **M2は約5,000〜33,000円**（標準で約13,000円）。H2・H3はツール呼び出しで何往復もするため、H0の数倍かかる。1か月にまとめて回すと、GPU代と合わせて月1万円を超える可能性が高い。
- Opus 5.5 は思考（extended thinking）を切れない。思考の量は `effort` で調整する。思考のトークンは出力として課金されるため、`effort` が費用を最も大きく左右する。
- Batch APIは半額になるが、待ち時間が長く（多くは1時間以内、最大24時間）、**速度（QCDのD）は測れない**。速度を測る実行は通常のAPIで行う。
- おすすめ：**APIキーを採用する。** 評価専用のワークスペースを作り、そこに月の利用上限（spend limit）をかける。キーは SSMパラメータストア（SecureString）に置く。API代は月1万円の内枠に入れ、M0の実測値を見てからM2の回し方（月をまたぐ、モデルを分けるなど）を決める。

## 1. 単価

### 1.1 モデル別の単価（100万トークンあたり、ドル）

| モデル | 入力 | キャッシュ書き込み（5分） | キャッシュ書き込み（1時間） | キャッシュ読み込み | 出力 |
|---|---|---|---|---|---|
| **Claude Opus 5.5** | **4** | 5 | 8 | 0.20 | **20** |
| Claude Sonnet 5.5 | 2 | 2.50 | 4 | 0.10 | 10 |
| Claude Haiku 5.5（入力10万トークンまで） | 0.10 | 0.125 | 0.20 | 0.01 | 0.50 |

- Opus 5.5 のキャッシュ読み込みは、入力単価の5%。
- 入力が長くても単価は変わらない（Opus 5.5 と Sonnet 5.5 は100万トークンまで同じ単価）。Haiku 5.5 だけは、入力が10万トークンを超えると単価が上がる。本件の入力はそこまで大きくならない。
- 米国内だけで推論させる指定（`inference_geo`）をすると1.1倍になる。既定（指定なし）なら通常の単価。
- 高速モード（fast mode）は Opus 5.5 で 8ドル／40ドル（2倍）。本件では使わない。

### 1.2 割引の仕組みと、本件に合うか

| 仕組み | 割引 | 本件に合うか |
|---|---|---|
| プロンプトキャッシュ | 読み込みは入力単価の5%。書き込みは1.25倍（5分）または2倍（1時間） | **H2・H3で効く。** 何往復もするたびに、画像と会話の履歴を送り直すため。H0は入力が小さく、効果は小さい |
| Batch API | 入力・出力とも50%引き。キャッシュの割引と重ねられる | **正確さの測定には使える。速度の測定には使えない**（下記） |

プロンプトキャッシュの注意点：

- キャッシュできる最小の長さは512トークン（Opus 5.5）。指示文（1,000〜3,000トークン）と画像を先頭に置けば対象になる。
- キャッシュは出力の内容を変えない。ただし、キャッシュが当たると応答が速くなる。**繰り返し実行の2回目以降だけ速く見える** ため、速度を比べるときは、キャッシュが当たったか（`cache_read_input_tokens`）を `run.yaml` に残し、当たった回と当たらなかった回を分けて集計する。

Batch APIの注意点：

- 多くは1時間以内に終わるが、最大24時間かかる。24時間で終わらなければ期限切れになる（期限切れの分は課金されない）。
- 待ち時間は混み具合で決まるため、**1回の実行時間は測れない**。QCDの速度を測る実行は、通常のAPIで行う必要がある。
- 往復するたびに1つのバッチになるので、H2・H3（ツール呼び出しで何往復もする）には向かない。
- 使い分けの案：正確さを見るための繰り返し（H0・H1）はBatch APIで半額にし、速度は通常のAPIで数回だけ測る。ただしM0は金額が小さいので、通常のAPIだけで十分。

## 2. 画像のトークン数

### 2.1 計算の仕方

- 画像は28×28ピクセルの区画（パッチ）単位で数える。トークン数は `⌈幅 ÷ 28⌉ × ⌈高さ ÷ 28⌉`。
- Opus 5.5 は高解像度の区分（Claude 4.7以降のモデル）に入る。上限は **長い辺 2,576ピクセル**、**1枚あたり4,784トークン**。
- どちらかの上限を超えると、縦横比を保ったまま自動で縮小される。ふつうの写真では、トークンの上限のほうで縮小が決まる。
- 1枚の画像の上限は 8,000×8,000ピクセル、10MB（base64にした後）。1回のリクエストに20枚を超える画像を入れると、1枚ごとの大きさの制限が厳しくなる（各辺2,000ピクセル以下にすれば安全）。

### 2.2 買取表の画像の場合（3段×7列＝21枚）

| 画像の大きさ | 処理される大きさ | トークン数 | 入力の費用（Opus 5.5） |
|---|---|---|---|
| 1,200×1,600 | 縮小なし | 2,494 | 約0.01ドル（約1.6円） |
| 1,500×2,000 | 縮小なし | 3,888 | 約0.016ドル（約2.5円） |
| 2,000×2,000 | 約1,932×1,932 に縮小 | 約4,761 | 約0.019ドル（約3円） |
| 2,400×1,800 | 約2,212×1,659 に縮小 | 約4,740 | 約0.019ドル（約3円） |

- **画像1枚の入力費用は数円で、全体の費用への影響は小さい。**
- 1枚の画像に21枚のカードが並ぶため、横2,000ピクセルでもカード1枚の幅は約285ピクセル。ワザ名やカード番号などの小さな文字は、つぶれて読めないことがある。
- 読み取りが足りない場合は、画像を2〜3枚に分けて送る（例：段ごとに切り出す）。トークン数は2〜3倍（1万〜1.5万トークン程度）になるが、費用は1回あたり数円の増加にとどまる。カード1枚を 400×560 ピクセルで切り出すと約300トークン。21枚分で約6,300トークン。
- JPEGの強い圧縮は文字を読みにくくする。送る前に、実際に送る画像を目で確認する。
- 送る前に自分で縮小しておくと、何が送られたかがはっきりする（座標を使う場合にも、ずれが起きない）。

## 3. H0の1回あたりのトークン数と費用

### 3.1 入力

| 中身 | トークン数の目安 |
|---|---|
| 指示文と出力形式の説明 | 1,000〜3,000 |
| 画像1枚 | 2,500〜4,800 |
| **合計** | **約4,000〜8,000** |

### 3.2 出力

**出力JSON（設計書 5.3 の形式）**

- カード1枚あたりの項目：位置、名前・HP・ワザ名、価格、状態、パック名、セットコード、番号、レアリティ、候補、確信度。
- 英数字と記号のキー名が多く、1トークンあたり約3文字。名前・ワザ名・パック名などの日本語は、1文字あたり約1トークン。
- 1枚あたり **約120〜200トークン**（改行と字下げのある整形済みのJSONだと多いほう）と見込む。
- 21枚で約2,500〜4,200トークン。全体の枠を足して **約3,000〜5,000トークン**。

**思考（extended thinking）**

- Opus 5.5 は思考を切れない（無効にする指定はエラーになる）。量は `effort`（`low`〜`max`）で調整する。既定は `medium`。
- 思考のトークンは出力として課金される。表示を省略（既定）しても、課金は同じ。
- 21枚を読み取って同定する作業では、思考は数千〜2万トークン程度と見込む。**実際の量は要確認**（M0の試行で `usage.output_tokens` を見て決める）。

### 3.3 1回あたりの費用（Opus 5.5、通常のAPI）

為替レートは **1ドル＝160円** とする（2026-10-07 の実勢は約158.4円。少し円安側に丸めた）。消費税などの扱いは要確認（下記）。

| 場合 | 入力 | 出力（JSON＋思考） | 費用（ドル） | 費用（円） |
|---|---|---|---|---|
| 少なめ（effort `low`） | 4,500 | 6,000（4,000＋2,000） | 約0.14 | **約22円** |
| 標準（effort `medium`） | 7,000 | 12,000（4,000＋8,000） | 約0.27 | **約43円** |
| 多め（effort `high`） | 8,000 | 25,000（5,000＋20,000） | 約0.53 | **約85円** |

- 出力の単価は入力の5倍。**費用の9割前後は出力**になる。
- 費用を下げる手段の順番：`effort` を下げる → 出力JSONを整形しない（字下げなし）→ 不要な項目を減らす。入力を削っても効果は小さい。

## 4. 場面ごとの見積もり

### 4.1 M0

- クラウドのモデル：1〜3タスク × 3回 ＝ 最大9回。
- 指示文や出力形式を直すための試行：20回程度。
- **合計30回程度**と見込む。

| 場合 | 1回 | 30回 |
|---|---|---|
| 少なめ | 約22円 | **約700円** |
| 標準 | 約43円 | **約1,300円** |
| 多め | 約85円 | **約2,600円** |

小さいモデルとして Sonnet 5.5 も同じ回数だけ回すと、さらに約650〜1,300円。**M0は、多めに見ても3,000〜4,000円以内**。

### 4.2 M2

前提：10タスク × H0〜H3 × 3回。H2・H3はカードDBの検索で何往復もする。

**H0に対する倍率（大まかな目安）**

| 段階 | 倍率 | 理由 |
|---|---|---|
| H0 | 1 | 基準 |
| H1（1枚ずつ読み取る） | 1.2〜2倍 | 1回で済むが、1枚ずつの記述が増え、出力と思考が長くなる |
| H2（照合） | 2〜4倍 | 何往復もする。往復ごとに、画像と履歴を送り直し、ツール呼び出しと思考を出力する |
| H3（自己検証） | 3〜6倍 | H2に加えて、確かめるための検索と読み直しが増える |

H2の計算例（標準）：8往復。往復ごとの入力は平均1.5万トークンで、大半はキャッシュから読む。出力は往復ごとに約2,000トークン、最後に出力JSONが約4,000トークン。

- 入力：約0.17ドル（キャッシュあり）。キャッシュがないと約0.48ドル。
- 出力：約2万トークン ＝ 約0.40ドル。
- 合計：約0.57〜0.88ドル ＝ H0の約2〜3倍。

ツールの定義も入力に加わる（ツールを使うときに自動で付く指示文は、Opus 5.5 で286トークン）。

**M2の合計**

| 場合 | 1回（H0） | 倍率の合計（H0〜H3） | 合計 |
|---|---|---|---|
| 少なめ | 約0.14ドル | 7.2（1＋1.2＋2＋3） | 約30ドル ＝ **約4,800円** |
| 標準 | 約0.27ドル | 10（1＋1.5＋3＋4.5） | 約81ドル ＝ **約13,000円** |
| 多め | 約0.53ドル | 13（1＋2＋4＋6） | 約207ドル ＝ **約33,000円** |

- タスクが増えれば比例して増える。標準で、**1タスク（H0〜H3 × 3回）あたり約1,300円**。
- H0・H1をBatch APIにすると、標準で約1,600円下がる（全体の1割強）。H2・H3が大半を占めるため、効果は限られる。
- 設計書 6.4 の流れでは、H1〜H3の本命は小さいモデルで、大きいモデルは H0 と H2・H3 だけでもよい。その場合、Opus 5.5 の分は標準で約11,000円。

### 4.3 実行の仕方による上乗せ（要確認）

- Claude Codeなどのエージェントの実行環境（設計書 6.1 のランタイム）を通してAPIキーで動かすと、その実行環境の指示文とツールの定義が、往復ごとに入力に加わる。大きさは要確認（数千〜数万トークンの可能性がある）。キャッシュが当たれば費用の増え方は小さいが、M0の試行で `usage` を確認する。
- H0を自作の実行スクリプトからAPIで直接呼ぶ場合は、上の見積もりのとおり。

## 5. 安いモデルとの比較（参考）

H0の1回（標準の場合、思考の量は同じと仮定）：

| モデル | 1回 | M0（30回） | M2（標準） |
|---|---|---|---|
| Opus 5.5 | 約43円 | 約1,300円 | 約13,000円 |
| Sonnet 5.5 | 約22円 | 約650円 | 約6,500円 |
| Haiku 5.5 | 約1円 | 約30円 | 約330円 |

- Sonnet 5.5 はちょうど半額。Haiku 5.5 は Opus 5.5 の約40分の1。

- 小さい文字の読み取りの精度は、モデルごとに確かめる必要がある。そもそも「大きいモデルと小さいモデルの差」を測るのが、このプロジェクトの目的の一つである。

## 6. APIキーの管理

### 6.1 利用上限と制限の枠

| 項目 | 内容 |
|---|---|
| 組織の月の上限 | 利用の段階（tier）ごとに決まっている。Start：500ドル、Build：1,000ドル、Scale：20万ドル |
| 自分で決める上限 | 組織全体にも、ワークスペースごとにも、上の上限より低い月の上限をかけられる。**既定のワークスペースには上限をかけられない** ので、評価専用のワークスペースを作る |
| 上限に達したとき | 自分で決めた上限なら HTTP 400（`invalid_request_error`）。段階の上限なら HTTP 429（`rate_limit_error`、`retry-after` なし）。SDKの自動再試行では回復しないので、実行スクリプトは「上限で止まった」と記録して終了する |
| 新しいアカウント | 最初は Evaluation tier になることがあり、表の標準の枠より低い。使った実績に応じて自動で上がる |
| 速度の枠（Start tier、Opus 5.5） | 1分あたり 1,000リクエスト、入力200万トークン、出力40万トークン。キャッシュから読んだ分は入力の枠に数えない。本件の規模では問題にならない |

設定の案：

- 評価専用のワークスペース（例：`tcg-buylist-eval`）を作り、そこでAPIキーを発行する。
- ワークスペースの月の上限は、まず **30ドル（約5,000円）** 程度にする。M2の前に見直す。
- 実行記録（`run.yaml`）には、`usage` の入力・出力・キャッシュ読み込み・キャッシュ書き込みのトークン数と、計算した費用を残す（設計書 5.5）。

### 6.2 キーの保管場所（AWS）

| 保管場所 | 費用 | 良い点 | 弱い点 |
|---|---|---|---|
| Secrets Manager | 1つのシークレットにつき月0.40ドル（約64円）＋ 1万回の呼び出しにつき0.05ドル | キーの自動更新（ローテーション）の仕組みがある | 有料。AnthropicのAPIキーは自動更新の仕組みがそのままでは使えず、利点を活かしにくい |
| SSMパラメータストア（標準・SecureString） | 保管も呼び出しも追加料金なし（標準の処理能力の場合） | 無料。暗号化して保管できる。IAMで読める人を絞れる | 自動更新の仕組みはない |

- **おすすめは SSMパラメータストアの SecureString**。本件はキーが1つで、自動更新も要らない。
- SecureString の暗号化に使うKMSの費用は、AWSが管理する鍵を使う場合は鍵の月額がかからない見込み。暗号を解く呼び出しの料金を含め、要確認。
- 実行環境には、起動時にIAMの権限で読み込ませる。キーをリポジトリ、Terraformの状態ファイル、ログに残さない。

## 7. サブスク（Claude Pro・Max）でサーバーから無人実行できるか

| 根拠 | 内容 |
|---|---|
| Claude Code の認証の説明 | `claude setup-token` で1年間有効のトークンを作り、環境変数 `CLAUDE_CODE_OAUTH_TOKEN` に入れれば、ブラウザでのログインなしに動かせる。「CIのパイプラインやスクリプト向け」と書かれており、Pro・Max・Team・Enterprise のプランが必要 |
| Claude Code の法令・規約の説明 | サブスクのログイン（OAuth）は、サブスクを買った本人が Claude Code などの Anthropic のアプリを **ふつうに使う** ためのもの。Pro・Max の利用枠は「ふつうの個人の使い方」を前提にしている。Agent SDK を使って製品やサービスを作る開発者は、APIキーを使うこととされている |
| 一般向けの利用規約（Consumer Terms） | 「APIキーで使う場合や、明示的に許可されている場合を除き」、ボットやスクリプトなど自動の手段でサービスを使ってはならない |

- 本人が自分のサーバーで、改変していない Claude Code を自分のサブスクで動かすこと自体は、トークンの仕組みが公式に用意されている。
- ただし、評価のための繰り返しの無人実行が「ふつうの個人の使い方」に入るかは、はっきりしない。**要確認**（必要ならAnthropicのサポートに問い合わせる）。
- 加えて、サブスクでは1回ごとの費用を正確に測れない。普段の作業と利用枠を取り合う。自作の実行スクリプトからAPIを直接呼ぶ使い方（H0）は、そもそもサブスクの対象外。
- 以上から、**本件はAPIキーにするのが確実**。

## 8. 予算との関係とおすすめ

| 場面 | API代（標準） | GPUの予算（月5,000円）と合わせた合計 | 月1万円に収まるか |
|---|---|---|---|
| M0 | 約1,300円（多めでも約3,000円） | 約6,300〜8,000円 | **収まる** |
| M2（1か月にまとめて回す） | 約13,000円（少なめ〜多めで約5,000〜33,000円） | 約18,000円 | **収まらない可能性が高い** |

おすすめ：

1. ADR-0006 は **APIキーを採用** してよい。M0の費用は小さく、トークン数と費用を正確に記録できる。
2. API代は **月1万円の内枠に入れる**。評価専用ワークスペースの上限を30ドル程度にかけ、超えないようにする。
3. M0の試行で、思考の量（`effort` ごとの出力トークン数）と1回の実費を測り、この見積もりを置き換える。
4. M2は、次のどれかで月の予算に収める。
   - 何か月かに分けて回す（例：devを先、testを後）。
   - Opus 5.5 は H0 と H2・H3 だけにし、H1〜H3 の本命は小さいモデルで回す。
   - 正確さの繰り返しは Batch API を使い、速度は通常のAPIで数回だけ測る。
   - `effort` を `low` または `medium` に固定する（評価の条件としても揃える）。

## 9. 確認できなかったこと（要確認）

- 実際の思考のトークン数（`effort` ごと）。M0の試行で測る。
- 日本語を含む出力JSONの正確なトークン数。トークン数を数えるAPI（`count_tokens`、無料）で、出力例を数えれば確かめられる。今回はAPIキーがないため数えていない。
