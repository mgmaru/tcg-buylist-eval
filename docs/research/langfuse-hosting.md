# Langfuseの置き場所とデータの扱い

調査日：2026-10-26

[ADR-0007](../adr/0007-use-langfuse-for-scoring-and-tracing.md) で未定になっている「どこで動かすか」「トレースの送り方」「画像を送ってよいか」「いつから使うか」を決めるための調査メモ。

## 結論

- **M0はLangfuseのクラウド版の無料プラン（Hobby）を、日本リージョンで使う。** M0の使用量は無料枠（月5万ユニット）の1%未満。M2でも、送り方を工夫すれば無料枠に収まる見込み。
- **自分で立てるのはM0では見送る。** 推奨構成（4コア・16GB）を常時動かすと月2万円を超え、予算（月1万円）に合わない。使うときだけ動かせば安いが、そのあいだしか画面を見られない。公式のTerraformモジュールは本番向けの大きな構成（EKSなど）で、月数万円になる見込み。
- **画像はLangfuseに送らない。** 代わりに、画像のハッシュ（SHA-256）とタスクIDだけをトレースに入れる。SDKの自動計測は使わず、両方のモデルの呼び出しを自作の薄いラッパーで同じ形のトレースにする。
- **M0から使い始めてよい。** ただし、正本はローカルのCSVとする（設計書 9章）。Langfuseには、ローカルの採点が動いたあとで、画像なしのトレースとスコアを送るところまでにとどめる。
- **機能の面では、Hobbyでも自分で立てる無料版（OSS版）でも、このプロジェクトに要る機能（データセット、実験と比較画面、自作のスコアの送信、トレース）はすべて使える。** 2025年6月に製品の機能はすべてMITになり、有料（ライセンスキーが必要）なのは監査ログ・SCIM・プロジェクト単位の権限・データ保持の設定などの企業向けの機能だけ。Hobbyの制限は、閲覧期間30日、2人、月5万ユニット、APIの回数、アノテーションのキュー1つ、という量の制限である（6章）。
- 画像をクラウド版に送ってよいかは、まだ判断できない（要確認）。決まるまでは送らない運用で困らない。

## 1. クラウド版のプラン

料金の単位は「ユニット」。Langfuseに送ったデータ1件（トレース、オブザベーション、スコア）が1ユニットになる。

| プラン | 月額 | 含まれるユニット | 超過分 | データを見られる期間 | ユーザー数 | リージョン |
|---|---|---|---|---|---|---|
| Hobby | 無料（カード登録不要） | 5万／月 | 買えない（超えたときの動きは要確認） | 30日 | 2人 | 米国・EU・日本 |
| Core | 29ドル | 10万／月 | 10万ごとに8ドル | 90日 | 無制限 | 米国・EU・日本 |
| Pro | 199ドル | 10万／月 | 10万ごとに8ドル | 3年 | 無制限 | 米国・EU・日本 |
| Enterprise | 2,499ドル | 10万／月 | 年契約で割引 | 3年 | 無制限 | 米国・EU・日本・HIPAA |

- 日本リージョンはAWSの東京（ap-northeast-1）。接続先は `jp.cloud.langfuse.com`。
- Hobbyで上限を超えたときに、受け付けが止まるのか、捨てられるのかは公式の記載が見つからない（要確認）。
- Hobbyの「30日」は見られる期間の上限で、データが消えるわけではない。一方、古いデータを自動で消す設定（データ保持の設定）はProとEnterpriseだけ。Hobbyでは手で消す（UIかAPIでトレースを削除できる）。
- Langfuseは2026年1月にClickHouse社に買収された。契約・DPAの相手はClickHouse社になっている。

### 使用量の見積もり

1回の実行で送るものの仮定：トレース1、オブザベーション（モデル呼び出しと処理の区切り）数件、スコア（同定正答率・誤答率・不明率・適合率など）5〜10件。

| 段階 | 実行回数 | 1回あたりのユニット | 月のユニット | 無料枠（5万）に対して |
|---|---|---|---|---|
| M0（H0、2モデル × 3タスク × 3回） | 18回 | 約10〜20 | 約200〜400 | 1%未満 |
| M0をやり直しも含めて5回まわす | 90回 | 約10〜20 | 約1,000〜2,000 | 2〜4% |
| M2（10タスク × 4構成 × 2モデル × 3回） | 240回 | 約30〜100（ツール呼び出しが増える） | 約7,000〜24,000 | 15〜50% |

- カード1枚ごとにスコアを送ると（買取表1枚に数十枚のカードが載る）、ユニットが数十倍になる。カードごとの判定はローカルのCSVに残し、Langfuseには実行ごとの集計値だけを送る。
- Claude Codeなどのエージェントのランタイムを使うと、ツール呼び出しのたびにオブザベーションが増える。M2で構成が増えたら、実際の使用量を見て見直す。

## 2. 自分で立てる場合

### 必要な部品

現在のバージョンはv4（2026年7〜8月に一般提供）。v3にはセキュリティ修正が2027年1月まで出る。

| 部品 | 役割 |
|---|---|
| Langfuse Web | 画面とAPI |
| Langfuse Worker | 受け取ったデータを裏で処理する |
| PostgreSQL | 設定やユーザーなどのデータ。v4では15以上（16を推奨） |
| ClickHouse | トレース・オブザベーション・スコア。v4で必要なバージョンは要確認 |
| Redis／Valkey | キャッシュと処理待ちの列。v4では7.0以上（7.2を推奨） |
| S3互換のストレージ | 受け取った生データと画像などの添付。docker composeではMinIOを使う |

### 構成ごとの費用（東京リージョン、1ドル＝150円で計算）

| 構成 | 内容 | 月の費用の目安 |
|---|---|---|
| EC2 1台＋docker compose（常時起動） | t3.xlarge（4コア・16GB、0.2176ドル／時間）＋ディスク | 約170ドル（約2.5万円）。予算を超える |
| EC2 1台＋docker compose（使うときだけ起動） | 月20時間動かす。ディスクは残す | 計算：約4.4ドル＋ディスク100GBで約9.6ドル＋公開IPを動かす時間分 ＝ 約15ドル（約2,000円）。ディスクを30GBにすれば約1,000円 |
| 公式のTerraformモジュール（EKSなど） | EKS（Fargate）、Aurora PostgreSQL Serverless v2、ElastiCache、S3、EFS、ALB、NATゲートウェイ | EKSだけで月約73ドル、NATゲートウェイで約45ドル。ClickHouseは初期設定で3台（2コア・8GB）。合計で数百ドルになる見込み（概算、要確認） |

- docker composeの推奨は「4コア・16GB以上、ディスクは使用量に応じて（例は100GB）」。公式に最低要件は示されていない。t3.large（8GB）で動くかは要確認。
- 公式は、docker compose構成を「冗長化・スケール・バックアップがない」としている。評価用の個人利用なら問題ないが、バックアップは自分で取る（EBSのスナップショットなど）。
- docker composeでは、ログのローテーションを設定しないとディスクがあふれることがある。

### 公式のTerraformモジュール

- AWS向けの公式モジュールがある（`langfuse/langfuse-terraform-aws`）。必須の入力は自分で管理するドメインだけ。
- 本番向けの構成で、常時動かす前提。使うときだけ作って消す運用には向かない。台数を減らせる設定はあるが、どこまで小さくできるかは記載がない。
- EC2 1台＋docker composeのTerraformは公式にはない。自作になる（[ADR-0004](../adr/0004-infrastructure-as-code.md) の練習としては手ごろ）。

### 作って消す運用でデータを残せるか

- できる見込み。docker composeのデータはDockerのボリュームに入るので、**データ用のEBSを別に作って残し、サーバーだけを作り直す** か、サーバーを消さずに停止する。
- 注意点：`docker compose down -v` はボリュームごと消す。Terraformでは、データ用のEBSに削除防止を付ける。
- 添付の保存先をMinIOではなくS3にすれば、画像などはS3に残る。ただし、PostgreSQLとClickHouseのデータはEBS側にある。
- サーバーを止めているあいだは、画面もAPIも使えない。実行スクリプトがトレースを送るときは、先にLangfuseを起動しておく必要がある。
- 画像の直接アップロードを使う場合、ストレージに外から名前解決できるホスト名が必要（SDKとブラウザが直接読み書きするため）。

## 3. 画像の扱い

### Langfuseの仕組み

| 送り方 | 何が起きるか | 画像の置き場所 |
|---|---|---|
| base64で埋め込む | SDKが検出して取り出し、Langfuseのストレージにアップロードする。トレースには参照用の文字列だけが残る | クラウド版はLangfuseのストレージ。自分で立てた場合は自分のS3 |
| 外部のURLを書く | アップロードされず、画面に表示するときにブラウザが元のURLから読む | 元の場所のまま |
| 自分のS3の参照（`s3://…`）を書く | 「外部メディアストレージ」という試験中の機能。プロジェクトに自分のバケットの読み取り用のキーを登録し、表示のときに署名付きURLで読む | 自分のS3のまま |
| 画像を送らない | 何も起きない | ローカルのみ |

- 同じ画像は、ハッシュ（SHA-256）で重複を除いて保存される。
- 外部メディアストレージは、組織の管理者が試験機能を有効にする必要がある。クラウド版で使えるか、どのプランで使えるか、画像をLangfuse側にコピーしないかは、明記がない（要確認）。
- Anthropic SDKの自動計測（OpenTelemetry）が画像をどう記録するかは、公式に記載がない（要確認）。リクエスト全体が記録され、base64の画像がそのまま入るおそれがある。

### 画像を除く方法

- PythonのSDKには、送る前にデータを書き換える関数（マスキング）を登録できる。送信前にクライアント側で動く。
- ただし、新しい方式のマスキングは「Langfuseの画像の処理のあとで動く」と書かれている。画像のアップロードが先に起きるかどうかは要確認。マスキングだけに頼らない。
- 確実なのは、**トレースに入れる入力を自分で組み立て、画像の部分を `{"type": "image", "sha256": "…", "task_id": "…"}` のような置き換えにする** こと。自動計測を使わなければ、画像が勝手に送られることはない。
- 画面で画像を見たいときは、ローカルの画像をタスクIDとハッシュで探す。

### クラウド版のデータの扱い

| 項目 | 内容 |
|---|---|
| 学習への利用 | プライバシーのFAQでは「顧客のデータでモデルを学習・微調整しない」としている |
| 製品の改善への利用 | クラウド版の追加条項（2026-04-10発効）では、AI機能（Langfuse内の任意のAI機能）の入出力を製品の改善に使える。学習・微調整には使わない。管理画面で止められる（止めた時点以降に効く） |
| DPA | ClickHouse社のDPAがある。契約の一部になる形。署名の手続きが要るかは記載がない（要確認） |
| 委託先 | ClickHouse社の委託先の一覧で公開。主な基盤はAWSとClickHouse Cloud |
| 削除 | トレースはUI・APIで1件ずつ・まとめて消せる（通常15分以内）。プロジェクトも消せる（大きいと数日）。トレースを消したときに画像も消えるかは記載がない（要確認） |
| 解約後 | 解約までに自分で消すか取り出す。バックアップなどからの完全な削除には最大30日 |
| 認証 | SOC 2 Type II、ISO 27001、GDPR対応 |

## 4. トレースの送り方

| 方法 | 内容 | このハーネスでの使いどころ |
|---|---|---|
| Langfuse Python SDK | 自分でトレースとオブザベーションを作る。新しいプロジェクトにはv5を推奨（Python 3.11以上、Langfuse v4が必要） | **本命。** 両方のモデルを同じ形で送れる |
| OpenTelemetry | `/api/public/otel` にOTLP（HTTP）で送る。認証は公開鍵と秘密鍵のBasic認証。gRPCは未対応。生成AIの標準の属性名を読む | ほかのツールがOpenTelemetryを出す場合の受け口 |
| Anthropic SDKの自動計測 | `opentelemetry-instrumentation-anthropic` を有効にするだけ | 手軽だが、画像が入るおそれがある。M0では使わない |
| OpenAI SDKの差し替え | `from langfuse.openai import OpenAI` に変えるだけ | 公式は「OpenAIとAzure OpenAIで動く」とだけ書いている。vLLMやOllamaなどの互換サーバーで正しく記録されるかは要確認。画像の扱いも記載なし |
| Claude Codeのプラグイン | Claude Codeの終了時のフック（Stop）で会話の記録を読み、トレースにする | Claude Code専用。ローカルのモデルのランタイムには使えない。SDKをv4系に固定する必要がある（v5と同じ環境に入れられない）。画像の扱いと除外の設定は記載なし |
| Inspect AI | Langfuseとの公式の連携はない。Inspectのフック（実行・サンプル・モデル呼び出しごとに呼ばれる）から、SDKで送る処理を自作できる見込み（Weights & BiasesやMLflowの例はある） | 実行の仕組みにInspectを選んだ場合（[ADR-0008](../adr/0008-execution-framework.md)） |

### 両方のモデルを同じ形で送る

- 実行スクリプトの中で、モデルの呼び出しを1つの関数にまとめる。その関数が、Anthropic APIでも、OpenAI互換のローカルのサーバーでも、同じ形のオブザベーション（種類は生成）を作る。
- 入れるもの：モデル名、構成名、タスクID、画像のハッシュ、置き換え済みの入力、出力のJSON、トークン数、時間。
- 構成名・モデル名・タスクIDは、絞り込みに使えるメタデータとして入れる。
- 短時間で終わるスクリプトでは、最後に `flush()` を呼ばないと送り漏れが出る。
- 注意：クラウド版は2026-11-16に古いAPIを廃止し、v4だけになる。Python SDKのv2は送れなくなり、v3も非推奨。v4以上（できればv5）を使う。

## 5. データセット・実験・スコア

- タスクセットをデータセットにし、構成ごとの実行を実験（データセットの実行）として比べられる。比較の画面がある。
- Python SDKの `run_experiment` は、Langfuseのデータセットがなくても、手元のデータ（入力と正解のリスト）で動く。各実行がトレースになる。
- データセットの項目に画像を付けることもできるが（SDK 4.10.0以上）、画像を送らない方針なので使わない。データセットには、タスクIDと正解データ（画像なし）だけを入れる。
- 自作の採点器のスコアは `create_score` で送る。型は数値・カテゴリ・真偽・テキスト。トレース単位、オブザベーション単位、セッション単位で付けられる。
- スコアの設定（名前、範囲、カテゴリ）を先に作っておくと、送るときに検査される。失敗の分類（設計書 9章）はカテゴリのスコアにできる。
- 同じスコアを送り直すときは、固定のIDを付けると上書きになる。
- スコアもユニットに数える（料金ページの説明による）。

## 6. クラウド版と自分で立てる場合の機能の違い

### ライセンス

- リポジトリの大半はMITライセンス。例外は `ee/`、`web/src/ee/`、`worker/src/ee/`、`packages/shared/src/server/ee/` の各フォルダで、別のライセンス（`ee/LICENSE`）になる。
- `ee/` 以下のコードも公開されているが、動かすにはライセンスキーが要る。環境変数 `LANGFUSE_EE_LICENSE_KEY` を、WebとWorkerの両方に設定する。
- 2025年6月に、それまで有料だった製品の機能（LLMによる採点の管理、アノテーションのキュー、プロンプトの実験、プレイグラウンド）がMITになった。2026年9月の公式の説明でも同じ扱いで、有料に戻った記録は見当たらない。
- 自分で立てる場合にライセンスキーが要る機能（2026-10時点）：

| 機能 | 内容 |
|---|---|
| プロジェクト単位の権限 | プロジェクトごとに役割を変える |
| 保護されたプロンプトのラベル | 本番用のラベルを変えられる人を限る |
| データ保持の設定 | 古いデータを自動で消す |
| 監査ログ | 誰が何をしたかの記録 |
| サーバー側のマスキング | 受け取った側でデータを書き換える |
| 画面のカスタマイズ | ロゴなど |
| 組織を作れる人の制限 | |
| 組織管理のAPIとSCIM | ユーザーの自動登録など |
| インスタンス管理のAPI | |
| FIPSモード | |

- 有償版の価格は個別見積もり。AWS Marketplaceか請求書で払う。
- 通常のSSO（Okta、Google、Azure AD、OIDC）はMIT側に入っている。ただし、`web/src/ee/` には `multi-tenant-sso` と `sso-settings` もある。画面から組織ごとにSSOを設定する機能はクラウド版向けとみられる（要確認）。個人利用では関係しない。

| サポート | なし | アプリ内（48時間） | GitHubのコミュニティ | 個別の契約 |

### APIの利用回数の制限（クラウド版）

| 種類 | Hobby | Core | Pro |
|---|---|---|---|
| データの受け付け | 1,000回／分 | 4,000回／分 | 20,000回／分 |
| 一般のAPI | 30回／分 | 100回／分 | 1,000回／分 |
| データセットのAPI | 100回／分 | 200回／分 | 1,000回／分 |
| オブザベーションのAPI（v2） | 30回／分 | 100回／分 | 1,000回／分 |
| 集計のAPI（v2） | 100回／日 | 100回／時間 | 500回／時間 |

- 自分で立てる場合、公式は「使用量の制限なし」としている。利用回数の制限を自分で設定できるかは要確認。
- SDKはトレースとスコアをまとめて送るので、受け付けの1,000回／分に当たることは、このプロジェクトの規模ではまずない。
- 当たりうるのは、比較表を作るためにAPIで結果を読み戻すとき。一般のAPIの30回／分と、集計のAPIの100回／日に注意する。比較表はローカルのCSVから作るので（設計書 9章）、問題になりにくい。

### このプロジェクトで要る機能

設計書 9章と [ADR-0007](../adr/0007-use-langfuse-for-scoring-and-tracing.md) で使うと決めた機能。

| 要る機能 | Hobby | 自分で立てる（OSS版） |
|---|---|---|
| タスクセットをデータセットにする | ◯ | ◯ |
| 構成ごとの実行を実験にする（SDKから） | ◯ | ◯ |
| 実験の比較画面 | ◯ | ◯ |
| 自作の採点器のスコアを送る（数値・カテゴリ） | ◯ | ◯ |
| スコアの設定（失敗の分類をカテゴリにする） | ◯ | ◯ |
| 失敗したタスクのトレースを見る | ◯ | ◯ |
| 人による評価（設計書の採点の一部） | △ キュー1つ。M0では足りる見込み | ◯ |

- **要る機能で、HobbyにもOSS版にもないものはない。** 違いは機能の有無ではなく、量と期間の制限（30日、2人、月5万ユニット、APIの回数）である。
- 30日を過ぎると、Hobbyでは古い実験を画面で見られなくなる。M0からM2まで実験を並べて比べたい場合に困る。正本のCSVがあるので、比較表そのものは作れる。
- 古いデータの自動削除は、HobbyにもOSS版にもない（ProかEnterprise）。どちらでも、消すときは手で消す。
- LLMによる採点をLangfuse上で動かす場合、モデルのAPIキーをLangfuseに登録し、料金は自分持ちになる。採点は自作の採点器で行う方針なので（設計書 8章）、使わない。

### 運用の違い（一人のプロジェクトとして）

| 項目 | クラウド版 Hobby | 自分で立てる |
|---|---|---|
| バージョンアップ | Langfuse側。何もしなくてよい | 自分。v3からv4のような大きな更新では、PostgreSQL・ClickHouse・Redisのバージョンも上げる必要がある |
| バックアップ | Langfuse側 | 自分（EBSのスナップショットなど）。docker composeにはバックアップの仕組みがない |
| 使えないとき | Langfuse側の障害のときだけ | サーバーを止めているあいだは、画面もAPIも使えない。実行の前に起動が要る |
| 立てる手間 | アカウントを作り、キーを発行するだけ | docker composeなら半日ほどの見込み（実測ではない）。公式のTerraformはEKSなどの大きな構成。EC2 1台のTerraformは自作 |
| 費用 | 無料 | 使うときだけ起動して月1,000〜2,000円。常時起動なら月2万円超（2章） |
| データの置き場所 | 東京（日本リージョン）。ClickHouse社が預かる | 自分のAWS |
| 古いSDKの廃止 | 2026-11-16に古いAPIを廃止。SDKをv4以上にする | 自分で上げるまで古いAPIも動く見込み（要確認）。ただし、v3へのセキュリティ修正は2027年1月まで |

### おすすめ

| 時期 | おすすめ | 理由 |
|---|---|---|
| M0 | クラウド版のHobby | 要る機能はすべて使える。使用量は無料枠の数%。バージョンアップとバックアップを気にしなくてよい。ハーネスづくりに時間を使える |
| M1〜M2 | Hobbyのまま続け、次のどれかが起きたら見直す | 30日より前の実験を画面で比べたくなった。画像をクラウド版に送れないと判断した。月5万ユニットに近づいた |
| 見直すとき | 自分で立てる（OSS版）を、EC2 1台＋docker composeで試す | OSS版には、要る機能も、Hobbyで制限のある機能（期間、人数、キューの数）もそろっている。費用は使うときだけ起動すれば月1,000〜2,000円で、Core（29ドル）より安い。ただし、止めているあいだは使えず、更新とバックアップは自分で行う |

- Enterpriseのライセンスキーで使える機能（監査ログ、SCIM、プロジェクト単位の権限、データ保持の設定など）は、一人のプロジェクトでは要らない。
- 自分で立てたあとでも、データの自動削除は使えない。消すときは手で消す。

## 7. M0での推奨

| 項目 | 推奨 | 理由 |
|---|---|---|
| どこで動かすか | クラウド版のHobby、日本リージョン | 費用ゼロ。使用量は無料枠に十分収まる。IaCとサーバーの管理が要らない。データの置き場所が東京になる |
| いつから使うか | M0から。ただしローカルの採点とCSV出力が動いてから | 送り方を早めに固めると、M1で手戻りが少ない。正本はCSVなので、30日の閲覧期間でも困らない |
| 画像 | 送らない。ハッシュとタスクIDだけ | 著作権の判断を待たずに始められる |
| 送り方 | Python SDKで自作のラッパーから送る。自動計測は使わない | 両方のモデルが同じ形になる。画像が勝手に送られない |
| 自分で立てる | M2以降に見直す | 画面で画像を見たくなった、クラウド版に送れないと判断した、無料枠を超えた、のどれかが起きたとき。そのときはEC2 1台＋docker composeを使うときだけ起動し、データ用のEBSを残す構成から試す |

## 8. まだ確認が必要なこと

- **画像の著作権**：設計書 13章が禁じているのは公開リポジトリへのコミット（公開）である。非公開のクラウドのサービスに保存することが、店舗の画像の扱いとして許されるかは判断できていない。なお、画像はAnthropicのAPIにも送るので、クラウド版のLangfuseに送ることと同じ種類の問題になる。両方を一緒に整理する必要がある。
- Hobbyで月5万ユニットを超えたときの動き。
- 外部メディアストレージ（自分のS3の参照）がクラウド版のHobbyで使えるか。画像がLangfuse側にコピーされないか。
- Anthropic SDKの自動計測と、OpenAI SDKの差し替えが、画像をどう記録するか。マスキングが画像のアップロードより先に動くか。
- OpenAI SDKの差し替えが、vLLMやOllamaで正しく記録されるか。
- トレースを消したときに、添付の画像も消えるか。
- DPAに署名の手続きが要るか。
- 自分で立てる場合：v4で必要なClickHouseのバージョン。t3.large（8GB）で動くか。公式モジュールの最小構成の実際の費用。
- 画面から組織ごとにSSOを設定する機能（`web/src/ee/` の `multi-tenant-sso`）が、自分で立てた場合に使えるか。
- 自分で立てた場合に、APIの利用回数の制限を設定できるか。
- サーバー側のマスキングが、クラウド版のどのプランで使えるか。
- Python SDK v5の具体的な関数名（ラッパーを書くときに公式ドキュメントで確かめる）。
